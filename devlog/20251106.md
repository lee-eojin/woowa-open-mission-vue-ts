# 2025-11-06 (3일차)

## 원본 데이터 파일 가져오기

본격적으로 구현을 시작하기 전에, 원본 미션의 데이터 파일을 가져와야 했다. 원본 레포지토리를 다운로드해서 확인해보니 `public/products.md`와 `public/promotions.md` 파일이 있었다. 파일 확장자는 `.md`지만 내용은 CSV 형식이었다.

## 데이터 처리 방식 고민

데이터를 어떻게 처리할지부터 일단 고민했다. 여러 방법을 찾아본 결과 세 가지로 좁혀졌다.

1. **원본 .md 파일 그대로 사용 + CSV 파싱**: fetch로 불러와서 CSV 파싱 로직 직접 구현
2. **JSON으로 변환**: .md를 .json으로 변환해서 바로 사용
3. **TypeScript 파일로 작성**: src/data/에 .ts 파일로 작성

처음에는 JSON이 편할 것 같았지만, 당시에 우테코에서 왜 `.md` 파일로 줬는지 생각해봤다. 실무에서는 데이터가 항상 깔끔한 형식으로 오지 않고, CSV나 텍스트 파일을 파싱해야 하는 경우가 많다. 우테코에서도 파일 입출력과 문자열 처리 능력을 평가하려는 의도였을 것이다.

원본 미션은 Node.js 환경에서 `fs` 모듈로 파일을 읽지만, 우리는 브라우저 환경이라 `fetch`를 사용해야 한다. 하지만 CSV 파싱 로직을 직접 구현하는 것은 동일하다. 결국 원본 의도를 살리면서도 웹 환경에 맞게 재해석하는 방향으로, `.md` 파일을 그대로 사용하고 fetch + CSV 파싱으로 구현하기로 했다.

## 데이터 파일 복사

원본 미션 폴더에서 `products.md`와 `promotions.md`를 `public/data/` 폴더에 복사했다. public 폴더에 있는 파일은 빌드 후에도 그대로 유지되고, fetch로 불러올 수 있다.

(프로모션 날짜가 2024년으로 되어있어서 2025년으로 수정했다. 지금 시점에서 사용하려면 유효한 날짜여야 프로모션 로직이 제대로 작동할 것 같았다.)

## TypeScript 타입 정의

CSV 파싱을 시작하기 전에, TypeScript의 타입부터 정의했다. `src/types/` 폴더에 `Product.ts`와 `Promotion.ts` 파일을 만들었다.

JavaScript였다면 그냥 객체를 만들어서 쓰면 되지만, TypeScript는 먼저 "이런 구조여야 한다"라는 것을 정의해야 한다. 예를 들어 Product는 name(문자열), price(숫자), quantity(숫자), promotion(문자열 또는 null)으로 구성된다고 `interface`로 선언했다.

이렇게 하면 나중에 `price`에 실수로 문자열을 넣거나, 필수 필드를 빼먹으면 바로 에러가 발생한다. IDE에서 자동완성도 지원되고, 리팩토링할 때도 안전하다. 처음에는 번거로워 보이지만 프로젝트가 커질수록 타입 시스템의 장점이 드러날 것 같다.

타입을 Product.ts, Promotion.ts, index.ts 세 파일로 분리한 이유는 각 타입을 독립적으로 관리하면서도, 사용할 때는 `import { Product, Promotion } from '@/types'` 한 줄로 가져올 수 있게 하기 위해서다. 객체지향 설계의 단일 책임 원칙을 타입 정의에도 적용한 셈이다.

## CSV 파싱 유틸리티 작성

타입 정의가 끝나고 나서, CSV 파일을 읽어서 타입에 맞게 변환하는 파서 함수들을 작성했다.

`src/utils/csvParser.ts`에 범용 CSV 파서를 만들고, `src/utils/productParser.ts`와 `src/utils/promotionParser.ts`에 각각 Product와 Promotion 전용 파서를 만들었다. 범용 파서는 CSV를 `Record<string, string>[]` 형태로 변환만 하고, 전용 파서들이 타입 변환과 유효성 검증을 담당한다.

처음에는 간단하게 작성했는데, TypeScript 컴파일러가 계속 `undefined` 가능성을 경고했다. 모든 필드에 대해 존재 여부를 먼저 검증하고, 그 다음 타입 변환과 값 유효성 검증을 하도록 수정했다. 에러 메시지도 `[ERROR]` 접두사를 붙이고 구체적인 값을 포함하도록 작성했다.

함수가 너무 길어져서 작은 함수들로 분리했다. `validateFields`, `validateValues`, `convertPromotionStringToNullable`, `createProduct` 같은 함수들로 나눠서 각 함수가 하나의 책임만 가지도록 했다. 우테코에서 강조하는 "한 메서드에 한 가지 일"을 실천하려고 노력했다.

## 객체지향으로의 대대적인 리팩토링

파서 함수들을 작성하고 나니, 문득 우리가 README에 "객체지향 설계 원칙을 최대한 따른다"고 적어놨다는 게 생각났다. 그런데 지금까지 만든 건 전부 함수 기반이었다. JavaScript로 우테코 미션 할 때는 클래스를 많이 썼는데, TypeScript에서도 클래스를 써야 진짜 객체지향이 아닐까?

### types → domain 폴더로 변경

먼저 폴더명을 바꿨다. `types`는 단순히 타입 정의만 있다는 느낌인데, 우리가 만들 건 비즈니스 로직을 포함한 도메인 모델이니까 `domain`이 더 적합하다고 판단했다. `models`도 고려했지만, README에 "도메인 개념"이라고 적어놨으니 `domain`이 더 명확하다.

### interface → class 변경

Product와 Promotion을 interface에서 class로 변경했다.

Product 클래스는 private readonly 필드로 캡슐화하고, getter 메서드들(`getName()`, `getPrice()` 등)과 비즈니스 로직 메서드들(`hasPromotion()`, `getTotalPrice()`)을 추가했다. 단순히 데이터만 담는 게 아니라 도메인 로직을 가진 객체가 된 것이다.

Promotion 클래스도 마찬가지로 만들었다. 특히 `isActive(currentDate)` 메서드를 추가해서 특정 날짜에 프로모션이 유효한지 확인할 수 있게 했다. 날짜 비교 로직을 클래스 내부에 캡슐화한 것이다.

### Parser 함수 → Parser 클래스 변경

utils 폴더의 파서 함수들도 전부 클래스로 바꿨다.

`CsvParser` 클래스는 `parse()` 메서드를 public으로 두고, 나머지 로직들(`splitLines`, `validateLines`, `extractHeaders`, `parseDataRows`, `parseRow`)을 private 메서드로 분리했다. 큰 함수를 작은 메서드들로 쪼개니 각 메서드의 책임이 명확해졌다.

`ProductParser`와 `PromotionParser` 클래스는 생성자에서 `CsvParser` 인스턴스를 만들어서 사용한다. 의존성을 명확히 관리하는 구조가 됐다. `NULL_STRING` 같은 상수는 `static readonly`로 선언해서 클래스 레벨 상수로 만들었다.

App.vue에서 사용할 때도 `new ProductParser()`로 인스턴스를 생성하고 `parse()` 메서드를 호출하는 방식으로 바뀌었다. 함수형보다 객체지향적인 코드가 된 것이다.

## 상수 관리 시스템 구축

리팩토링을 하다 보니 에러 메시지가 코드 곳곳에 흩어져 있는 게 눈에 띄었다. 나중에 메시지를 수정하려면 여러 파일을 뒤져야 할 것 같았다.

`src/constants/` 폴더를 만들고 `errorMessages.ts`와 `validationRules.ts`로 상수들을 분리했다. 처음에는 파일명을 `messages.ts`, `validation.ts`로 했다가, 더 명확하게 `errorMessages.ts`, `validationRules.ts`로 바꿨다.

에러 메시지는 도메인별로 계층 구조로 만들었다. `ERROR_MESSAGES.CSV`, `ERROR_MESSAGES.PRODUCT`, `ERROR_MESSAGES.PROMOTION` 이런 식으로. 함수 형태의 메시지도 지원해서 `INVALID_PRICE: (value: string) => ...` 같은 동적 메시지도 가능하게 했다.

`as const`로 TypeScript 타입 레벨 불변성도 보장했다.

## TypeScript의 장점 체감

오늘 작업하면서 TypeScript의 장점을 확실히 느꼈다. 바닐라 JavaScript로 우테코 미션 할 때는 런타임에 터지고 나서야 에러를 발견했는데, TypeScript는 코드 작성하는 순간 빨간 줄로 알려준다. 특히 리팩토링할 때 클래스명이나 메서드명을 바꾸면 영향받는 모든 곳에 에러가 표시돼서 누락 없이 수정할 수 있었다.

처음에는 `undefined` 체크를 계속 요구해서 귀찮았는데, 나중에 생각해보니 런타임 에러를 미리 방지해준 거였다. 타입 시스템이 든든한 안전망 역할을 해주는 느낌이다.
