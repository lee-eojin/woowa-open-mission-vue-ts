# 2025-11-09 (6일차)

## 학습을 실전에 적용하는 날

어제 Vue 컴포넌트 설계를 공부했으니 오늘은 본격적으로 기능을 만들기로 했다. 지금까지 만든 도메인 클래스들을 실제 UI와 연결해서 사용자가 상품을 장바구니에 담고, 가격을 확인할 수 있게 만드는 것이 목표였다.

게다가 사실 프로젝트 초반부터 Pinia를 설치해놓고도 거의 일주일동안 한 번도 안 써봤다는 게 마음에 걸렸다. 상태관리가 왜 필요한지, Pinia를 어떻게 쓰는지 제대로 알아보고 싶었다.

## 왜 상태관리가 필요한가

본격적으로 시작하기 전에 먼저 고민한 부분이 있다. 장바구니 데이터를 어디에 둘 것인가?

가장 간단한 방법은 App.vue에 ref로 선언하고 props로 내려주는 것이다. 하지만 이렇게 하면 ProductList와 CartSummary가 모두 App.vue를 거쳐야 한다. 나중에 결제 화면이나 영수증 컴포넌트를 추가하면 props drilling이 심해질 것 같았다.

Vue 공식 문서에서 상태관리 섹션을 읽어봤다. 여러 컴포넌트가 같은 데이터를 공유해야 할 때, 특히 깊게 중첩된 컴포넌트 구조에서는 전역 상태관리가 필요하다고 나와있었다.

우리 프로젝트로 보면 장바구니는 상품 목록 화면, 결제 화면, 영수증 화면에서 모두 접근해야 한다. 이런 경우가 정확히 전역 상태관리가 필요한 시점이다.

## Pinia 학습 시작

Pinia 공식 문서를 정독했다. Vuex의 차세대 버전이라고 하는데, TypeScript 지원이 훨씬 좋고 API가 단순하다는 장점이 있다고 한다.

Pinia의 핵심 개념은 크게 세 가지다.

첫째, State는 데이터 저장소다. ref나 reactive로 선언한다.

둘째, Getters는 computed 프로퍼티와 비슷하다. state를 가공해서 반환한다.

셋째, Actions는 메서드다. state를 변경하거나 비동기 작업을 처리한다.

Vuex는 mutations와 actions를 구분했는데, Pinia는 actions만 있다. 훨씬 간단해졌다.

## Composition API 스타일로 Store 작성하기

Pinia는 두 가지 스타일을 지원한다. Options API 스타일과 Composition API 스타일이다.

Options API 스타일은 Vuex와 비슷하게 state, getters, actions를 객체로 정의하는 방식이다. 익숙하긴 한데, 우리 프로젝트가 Composition API를 쓰고 있으니까 store도 같은 스타일로 맞추는 게 일관성 있을 것 같았다.

Composition API 스타일은 setup 함수처럼 작성한다. ref로 state를 선언하고, computed로 getters를 만들고, 일반 함수로 actions를 정의한다. 그리고 마지막에 return으로 외부에 노출할 것들을 명시한다.

```typescript
export const useCartStore = defineStore('cart', () => {
  const cart = ref<Cart | null>(null)

  const items = computed(() => {
    if (!cart.value) return []
    return cart.value.getItems()
  })

  const addItem = (product: Product, quantity: number) => {
    cart.value.addItem(product, quantity, inventory.value)
  }

  return { items, addItem, ... }
})
```

이 방식이 컴포넌트 작성하는 것과 똑같아서 이해하기 쉬웠다.

## 도메인 클래스를 Store에 래핑하기

여기서 설계 고민이 좀 생겼다. 우리는 이미 Cart 도메인 클래스를 만들어놨다. 이걸 Pinia store에서 어떻게 활용할 것인가?

일단 최종적으로는 두 가지 방법을 생각해봤다.

첫 번째는 Cart 클래스를 완전히 해체해서 Pinia state로 옮기는 것이다. items를 ref로 선언하고, addItem, removeItem 같은 메서드들을 store actions로 다시 구현한다. 이렇게 하면 순수하게 Pinia만 사용하는 구조가 된다.

두 번째는 Cart 클래스를 그대로 유지하고, store는 단순히 Cart 인스턴스를 감싸는 래퍼 역할만 하는 것이다. state는 Cart 인스턴스 하나만 가지고, actions는 Cart 메서드를 호출만 한다.

고민 끝에 두 번째 방법을 선택했다. 이유는 여러 가지다.

첫째, 도메인 로직과 상태관리를 분리할 수 있다. Cart 클래스에는 비즈니스 규칙이 담겨있다. 프로모션 할인 계산, 재고 검증 같은 로직들이다. 이런 로직을 store에 섞으면 관심사가 뒤섞인다.

둘째, 테스트하기 쉽다. Cart 클래스는 순수 TypeScript 클래스라서 Pinia 없이도 테스트할 수 있다. 나중에 유닛 테스트 작성할 때 유리하다.

셋째, 재사용 가능하다. 만약 나중에 Node.js 백엔드를 만들거나, React로 포팅한다면 Cart 클래스는 그대로 쓸 수 있다.

결국 store는 전역 상태 관리만 담당하고, 실제 비즈니스 로직은 도메인 클래스가 처리하는 구조로 만들었다. 이게 아키텍처 측면에서 더 깔끔하다고 판단했다.

## Computed와 Getter 활용

store에서 computed를 사용하는 부분이 흥미로웠다.

```typescript
const items = computed<CartItem[]>(() => {
  if (!cart.value) return []
  return cart.value.getItems()
})
```

이렇게 하면 cart가 변경될 때마다 items가 자동으로 업데이트된다. 컴포넌트에서 cartStore.items를 참조하면 항상 최신 상태가 보장된다.

totalPrice, promotionDiscount, finalPrice도 모두 computed로 만들었다. 실제 계산은 Cart 클래스의 메서드가 하고, store는 그 결과를 reactive하게 노출만 한다.

이렇게 하니 컴포넌트에서는 그냥 cartStore.totalPrice만 쓰면 되고, 값이 변경되면 자동으로 화면이 업데이트된다. Vue의 반응형 시스템과 도메인 클래스가 자연스럽게 연결됐다.

## ProductTableRow에 담기 기능 추가

상품 목록에서 장바구니에 담는 기능을 구현했다.

처음에는 간단하게 버튼만 추가하려고 했는데, 사용자가 수량을 선택할 수 있어야 할 것 같아서 input도 함께 넣었다.

```vue
<input
  v-model.number="quantity"
  type="number"
  min="1"
  :max="product.quantity"
  class="quantity-input"
/>
<button @click="addToCart" class="add-to-cart-button">담기</button>
```

v-model.number를 써서 자동으로 숫자 타입으로 변환되게 했다. .number modifier가 없으면 문자열로 들어와서 타입 에러가 날 수 있다.

max 속성을 product.quantity로 설정해서 재고보다 많은 수량을 입력할 수 없게 했다. 하지만 브라우저의 기본 검증은 우회할 수 있으니까, addToCart 함수에서 한 번 더 검증한다.

```typescript
const addToCart = () => {
  try {
    cartStore.addItem(props.product, quantity.value)
    alert(`${props.product.name} ${quantity.value}개를 장바구니에 담았습니다!`)
    quantity.value = 1
  } catch (error) {
    if (error instanceof Error) {
      alert(error.message)
    }
  }
}
```

try-catch로 에러를 잡아서 alert으로 보여준다. 나중에 토스트 알림으로 바꿀 예정이지만, 지금은 빠르게 확인하기 위해 alert을 썼다.

성공하면 quantity를 1로 초기화한다. 같은 상품을 또 담을 때 편하게 하기 위해서 그랬ㄱ다.

## CartSummary 컴포넌트 구현

장바구니 요약을 보여주는 컴포넌트를 만들었다.

이 컴포넌트는 오직 cartStore만 바라본다. props를 전혀 받지 않는다. 전역 상태관리의 장점이 바로 이것이다. 컴포넌트가 필요한 데이터를 직접 가져올 수 있다.

```typescript
const cartStore = useCartStore()
```

한 줄이면 끝이다. 이제 cartStore.items, cartStore.totalPrice 같은 걸 바로 쓸 수 있다.

장바구니가 비었을 때와 차있을 때를 v-if로 분기했다.

```vue
<div v-if="cartStore.isEmpty" class="empty-cart">
  <p>장바구니가 비어있습니다.</p>
</div>

<div v-else class="cart-content">
  <!-- 장바구니 내용 -->
</div>
```

isEmpty는 computed로 만든 getter라서 reactive하다. 상품을 하나 담으면 자동으로 v-else 쪽이 렌더링된다.

가격 표시 부분에서 toLocaleString을 사용해서 천 단위 콤마를 넣었다. 1000이 1,000으로 표시된다. 한국 사람들에게 익숙한 형식이다.

프로모션 할인이 있을 때만 할인 금액을 표시하도록 v-if를 썼다.

```vue
<div v-if="cartStore.promotionDiscount > 0" class="summary-row discount">
  <span>프로모션 할인</span>
  <span class="summary-value">-{{ formatPrice(cartStore.promotionDiscount) }}원</span>
</div>
```

할인이 0원이면 이 줄 자체가 렌더링되지 않는다. 불필요한 정보를 숨겨서 UI를 깔끔하게 유지한다.

## 레이아웃 설계

App.vue에서 상품 목록과 장바구니를 나란히 배치하기 위해 CSS Grid를 사용했다.

```css
.container {
  display: grid;
  grid-template-columns: 1fr 400px;
  gap: 2rem;
}
```

왼쪽은 1fr로 남은 공간을 모두 차지하고, 오른쪽은 400px 고정이다. 상품 목록이 메인이고 장바구니는 사이드바 느낌이다.

반응형도 고려했다. 화면이 좁아지면 세로로 배치된다.

```css
@media (max-width: 1024px) {
  .container {
    grid-template-columns: 1fr;
  }
}
```

모바일에서는 위아래로 스크롤하는 게 더 자연스럽다.

## 실시간 반응형 시스템 체감

구현하고 나서 브라우저로 확인했는데, 진짜 신기했다.

상품에서 수량 입력하고 담기 버튼 누르면, 장바구니에 즉시 나타난다. 총 금액, 프로모션 할인, 최종 금액이 전부 자동으로 계산된다. 삭제 버튼 누르면 바로 사라지고 가격도 다시 계산된다.

코드에서는 cartStore.addItem만 호출했을 뿐인데, 연결된 모든 부분이 자동으로 업데이트된다. 이게 Vue의 반응형 시스템이구나 싶었다.

특히 프로모션 할인 계산이 실시간으로 되는 게 인상적이었다. 콜라를 3개 담으면 1+1 프로모션이 적용돼서 할인 금액이 나타난다. 도메인 클래스에서 계산한 결과가 Pinia store를 거쳐 컴포넌트까지 자동으로 전달된다.

## 에러 처리와 검증

재고보다 많은 수량을 담으려고 하면 에러가 발생한다. Inventory.validateStock 메서드가 에러를 던지고, ProductTableRow의 try-catch가 잡아서 alert으로 보여준다.

```
[ERROR] 재고가 부족합니다. 상품: 콜라, 요청 수량: 100
```

도메인 클래스에서 정의한 에러 메시지가 그대로 사용자에게 전달된다. 에러 메시지를 constants/errorMessages.ts에 중앙화해놓은 게 빛을 발한다.

나중에는 이 에러 처리를 개선해야겠다고 생각했다. alert 대신 토스트 알림을 쓰고, 에러 로깅도 추가하고, 사용자 친화적인 메시지로 바꿔야 할 것 같다.

## 아키텍처 정리

오늘 만든 구조를 정리해보면 이렇다.

제일 안쪽에 도메인 클래스가 있다. Cart, CartItem, Inventory, Product, Promotion 같은 것들이다. 이들은 비즈니스 로직만 담당하고, Vue나 Pinia에 대해 전혀 모른다.

그 위에 Pinia store가 있다. cartStore는 Cart 인스턴스를 감싸서 전역 상태로 만들어준다. 도메인 클래스의 메서드를 호출하고, 결과를 reactive하게 노출한다.

제일 바깥에 Vue 컴포넌트가 있다. ProductTableRow, CartSummary 같은 컴포넌트들이 store를 통해 데이터를 읽고 쓴다.

각 레이어가 명확하게 분리됐다. 도메인 로직, 상태관리, UI가 각자 책임만 가진다. 나중에 어느 한 부분을 바꿔도 다른 부분에 영향이 적을 것 같다.

이게 바로 레이어드 아키텍처구나 싶었다. 우테코에서 디스코드를 통해 배운 개념이 Vue 프로젝트에도 그대로 적용된다.

---

Pinia를 실전에서 써보니 상태관리가 왜 필요한지 확실히 알게 됐다. props drilling 없이 깔끔하게 데이터를 공유할 수 있다.

Composition API 스타일의 store가 생각보다 직관적이었다. 컴포넌트 작성하는 방식과 똑같아서 학습 곡선이 낮았다고 생각한다.

도메인 클래스와 상태관리를 분리하는 패턴이 좋다는 걸 체감했다. 비즈니스 로직은 순수하게 유지하고, store는 그걸 reactive하게 만드는 역할만 한다. 관심사 분리가 제대로 된 구조다.

Vue의 반응형 시스템이 정말 강력하다는 걸 느꼈다. 데이터를 변경하면 자동으로 UI가 업데이트되는 게 마법 같다. 하지만 마법이 아니라 잘 설계된 시스템이다.

에러 처리도 레이어별로 책임이 있다는 걸 배웠다. 도메인에서 에러를 던지고, 컴포넌트에서 잡아서 사용자에게 보여준다. 각자 자기 역할을 한다.
