# 2025-11-13 - Vitest 학습 노트

## Vitest란?

우테코 1-3주차에서 Jest를 썼었다. describe, it, expect로 테스트를 작성하고, npm test로 실행했다.

Vitest는 Jest와 거의 똑같다. describe, it, expect가 전부 똑같이 작동한다. 로또 프로젝트에서 작성한 테스트 코드를 거의 그대로 가져올 수 있다. API가 호환되기 때문이다.

Vite와 잘 맞기 때문이기도 하고 새로운 걸 써보려고 결정했다.

Jest를 쓸 때 불편한 점이 있었다. jest.config.js를 만들어야 하고, TypeScript를 쓰려면 ts-jest 설정을 추가해야 하고, 경로 alias를 쓰려면 moduleNameMapper를 또 설정해야 했다. 프로젝트 설정과 테스트 설정이 따로 놀았다.

Vitest는 이런 중복이 없다. 이미 vite.config.ts가 있다면 그 설정을 그대로 쓰면된다. TypeScript 설정, 경로 설정, 플러그인 설정이 전부 자동으로 적용된다. vitest.config.ts에서 vite.config.ts를 merge하면 끝이다.

실행 방식도 좀 다르다. Jest는 npm test를 치면 전체 테스트를 한 번 실행하고 끝난다. 테스트를 다시 돌리려면 명령어를 다시 쳐야 한다. Vitest는 watch mode가 기본이고 파일을 저장하면 관련 테스트가 자동으로 돌아간다. 코드 수정하고 저장하면 바로 테스트 결과가 나온다. npm run dev처럼 계속 켜두고 쓰는 느낌이다.

속도도 차이가 난다. Jest는 모든 파일을 변환하고 번들링한다. Vitest는 Vite의 빠른 번들러를 쓰고 필요한 부분만 변환한다. 작은 프로젝트에서는 차이가 안 느껴지지만 프로젝트가 커지면 Vitest가 확실히 빠르다.

즉, Vitest는 Jest와 같은데 Vite 프로젝트에 최적화되어 있다. Jest를 써봤다면 바로 쓸 수 있다.

## 프로젝트 현재 상태

프로젝트에는 이미 Vitest 관련 패키지가 설치되어 있다. vitest, @vue/test-utils, jsdom, @types/jsdom이 devDependencies에 들어가 있다. vitest.config.ts도 이미 설정되어 있는데, vite.config.ts를 mergeConfig로 합쳐서 사용한다. environment는 jsdom으로 되어 있어서 DOM 환경 시뮬레이션이 가능하다. Vue 컴포넌트를 테스트하려면 DOM이 필요하기 때문이다. 실행 스크립트는 test:unit이 vitest로 연결되어 있다.

## 테스트 작성 기본

테스트 파일은 src/**tests**/에 모아두면 한눈에 보기 편하다. Product.test.ts, Cart.test.ts 같은 식으로 파일명에 .test.나 .spec.을 포함하면 Vitest가 자동으로 인식한다.

테스트는 describe로 그룹을 만들고, 그 안에 it으로 개별 테스트를 작성한다. test도 it과 동일하게 사용할 수 있다. 각 테스트는 AAA 패턴을 따르는데, Arrange에서 테스트 데이터를 준비하고, Act에서 테스트할 동작을 실행하고, Assert에서 결과를 검증한다.

검증할 때는 expect 함수를 사용한다. toBe는 원시값 비교에, toEqual은 객체나 배열의 깊은 비교에 사용한다. toThrow는 에러 발생을 검증하는데, 함수를 화살표 함수로 감싸서 expect에 넘긴다. 특정 에러 메시지를 확인하고 싶으면 toThrow('에러 메시지')처럼 인자를 넘기면 된다. toBeNull, toBeDefined, toBeTruthy 같은 다양한 matcher 함수들도 있다.

## 테스트 작성 도구

여러 테스트에서 반복되는 설정이 있다면 beforeEach로 처리할 수 있다. beforeEach는 각 테스트 전에 실행되고, afterEach는 각 테스트 후에 실행된다. beforeAll은 전체 describe 블록 시작 전 한 번만 실행되고, afterAll은 전체 describe 블록 종료 후 한 번만 실행된다. 이를 활용하면 테스트 데이터 준비를 효율적으로 할 수 있다.

에러가 발생해야 하는 경우에는 재고 부족이나 잘못된 입력 같은 예외 상황을 검증할 때 유용하다. Vue 컴포넌트 테스트는 @vue/test-utils의 mount를 사용한다. mount는 컴포넌트를 마운트해서 wrapper 객체를 반환하고, wrapper.text()로 렌더링된 텍스트를 가져오거나 wrapper.find()로 DOM 요소를 찾을 수 있다. trigger()로 클릭 같은 이벤트를 발생시키고, emitted()로 발생한 이벤트를 확인한다.

## 좋은 테스트 작성 원칙

테스트는 독립적이어야 한다. 각 테스트는 다른 테스트에 영향을 받거나 주지 않아야 한다. 테스트 이름은 명확해야 한다. 무엇을 테스트하는지 바로 알 수 있게 작성한다. it('works', () => {})는 나쁜 예이고, it('프로모션 재고를 우선 차감한다', () => {})가 좋은 예다.

하나의 테스트는 하나만 검증한다. 한 번에 여러 기능을 테스트하지 말고, 각각 분리한다. 테스트 커버리지보다 중요한 건 품질이다. 100% 커버리지가 목표가 아니라, 중요한 로직이 제대로 작동하는지 검증하는 게 목표이다.

## 도메인 테스트 계획

프로젝트의 도메인 클래스는 Product, Promotion, CartItem, Inventory, Cart, PromotionPolicy가 있다. 이 클래스들의 비즈니스 로직을 테스트해야 한다.

Product는 생성자, hasPromotion, getTotalPrice를 테스트한다. readonly 필드로 불변성이 유지되는지도 중요하다. Promotion은 getTotalQuantity가 buy + get을 반환하는지, isActive가 날짜 범위를 정확히 체크하는지, calculateDiscount가 올바른 할인 금액을 계산하는지 확인한다. 2+1 프로모션에서 6개를 구매하면 2세트가 완성되므로 2개 무료, 즉 2000원 할인이 되어야 한다.

Inventory는 findByName, getPromotionStock, getNormalStock를 확인하고, 특히 validateStock이 재고 부족 시 에러를 던지는지, decreaseStock이 프로모션 재고를 우선 차감하는지가 중요하다. 프로모션 재고 5개, 일반 재고 10개인 상태에서 7개를 차감하면 프로모션 재고가 0이 되고 일반 재고는 8이 되어야 한다.

Cart는 addItem, getTotalPrice, getPromotionDiscount, getMembershipDiscount, getFreeItems, checkout을 테스트한다. 멤버십 할인은 최대 8000원이라는 제약이 있어서 50000원 \* 30% = 15000원이 나와도 8000원만 할인되어야 한다. PromotionPolicy는 findApplicablePromotion, canGetAdditionalFreeItem, calculateFullPriceQuantity를 검증한다.

우선순위는 도메인 로직이 가장 높고, 파서 테스트가 중간, 컴포넌트 테스트가 낮다.

## 실제 테스트 코드 참고 - 3주차 로또 프로젝트

이전에 작성했던 로또 프로젝트의 테스트 코드를 참고하면 실제로 어떻게 작성하는지 감을 잡을 수 있다.

로또 프로젝트에서 Lotto 클래스는 로또 번호를 관리한다. 테스트에서는 번호 개수가 6개를 넘으면 예외가 발생하는지, 중복된 숫자가 있으면 예외가 발생하는지, 번호가 오름차순으로 정렬되는지, 당첨 번호와 일치하는 개수를 반환하는지 검증했다. 테스트 이름이 명확해서 무엇을 테스트하는지 한눈에 들어온다. 에러 테스트가 많은 이유는 입력 검증이 중요한 도메인이기 때문이다.

PrizeCalculator 클래스는 당첨 금액과 수익률을 계산한다. 테스트에서는 수익률 계산, 소수점 반올림, 총 당첨 금액 계산을 구체적인 수치로 검증했다. 비즈니스 로직의 정확성을 숫자로 확인하는 것이다.

WinningNumbers 클래스는 당첨 번호와 보너스 번호를 관리한다. 여기서는 not.toThrow()를 사용해서 정상 케이스도 테스트했다. 예외가 발생하지 않는 것도 중요한 테스트 케이스다.

로또 프로젝트와 편의점 프로젝트는 비슷한 구조를 가진다. Lotto와 Product는 도메인 값 객체다. PrizeCalculator와 Cart는 계산 로직을 담당한다. WinningNumbers와 Inventory는 컬렉션 역할이다. 테스트 작성 방식도 비슷할 것이다. 입력 검증, 반환값 확인, 계산 로직 검증 같은 패턴을 똑같이 적용하면 된다.

차이점은 편의점 프로젝트가 TypeScript라는 점이다. 타입이 명시되어 있어서 일부 검증은 컴파일 타임에 이루어진다. 하지만 비즈니스 로직은 여전히 런타임 테스트가 필요하다.
