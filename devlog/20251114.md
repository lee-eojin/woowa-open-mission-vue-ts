# 2025-11-14 - 테스트 작성과 리팩토링

## 테스트를 작성하기 전에

오늘은 도메인 클래스들의 단위 테스트를 작성하기로 했다. 어제 Vitest를 공부하면서 테스트 작성 방법을 익혔고, 오늘은 실제로 적용하는 날이다.
작은 단위부터 시작해서 Product와 Promotion을 테스트하고, 그 다음 복잡한 Inventory를 리팩토링하면서 테스트로 안전성을 검증하는 방식이다.

## Product 테스트 작성

Product는 가장 단순한 도메인 클래스다. 값 객체에 가깝다. 처음에는 생성자 테스트를 포함해서 4개 테스트를 작성했다.

```typescript
it('생성자가 올바르게 값을 할당한다', () => {
  const product = new Product(PRODUCT_NAME, PRODUCT_PRICE, PRODUCT_QUANTITY, PROMOTION_NAME)

  expect(product.name).toBe(PRODUCT_NAME)
  // ...
})
```

음 그런데 작성하고나니까 생성자 테스트가 솔직히 의미가 있나 싶었다. TypeScript는 타입 안전성을 컴파일 타임에 보장한다. 생성자가 값을 제대로 할당하는지는 타입 시스템이 이미 검증한다. (귀찮아서 그런게 아니라) 런타임 테스트로 다시 확인할 필요가 있을까?

로또에서는 JavaScript였기 때문에 생성자 테스트가 의미가 있었다. 하지만 TypeScript에서는 다르다. 실질적인 비즈니스 로직만 테스트하는 게 맞다고 판단했다. hasPromotion과 getTotalPrice만 남기고 생성자 테스트는 지웠다. 최종적으로 3개 테스트가 되었다.

## 상수화 고민

테스트 데이터를 상수로 빼야 하는지도 고민했다.

'콜라', 1000, 10 같은 값들은 일단 PRODUCT_NAME, PRODUCT_PRICE, PRODUCT_QUANTITY로 상수화하였다. 나중에 프로젝트 전체 constants로 빼야 하나 고민했는데, 테스트 데이터는 테스트 파일 내부에 두는 게 일반적이라는 결론을 내렸다. 각 테스트가 독립적이어야 하고, 테스트마다 필요한 데이터가 다를 수 있기 때문이다.

하지만 expect(discount).toBe(2000) 같은 예상 결과값까지 상수화하지는 않았다. 2000은 계산 결과이고, 테스트에서 바로 보는 게 더 명확하다. 이게 왜 2000인지는 테스트 로직에서 드러나야 한다.

## Promotion 테스트와 beforeEach 도입

Promotion 테스트를 작성하면서 중복이 보이기 시작했다. 모든 테스트에서 동일한 Promotion 인스턴스를 생성하고 있었다. 8개 테스트 모두에서 new Promotion(...)을 반복했다.

이때 beforeEach를 사용하기로 했다. 로또 프로젝트에서는 각 테스트가 완전히 독립적이게 만들려고 beforeEach를 안 썼었다. 하지만 생각해보니 Promotion 같은 불변 객체는 beforeEach로 만들어도 문제가 없다. 각 테스트가 promotion을 수정하지 않으니까.

```typescript
let testPromotion: Promotion

beforeEach(() => {
  testPromotion = new Promotion(...)
})
```

변수명도 고민했다. testPromotion으로 명확하게 했다. 테스트용 데이터라는 의미를 담았다.

## Inventory 리팩토링의 필요성

Inventory 테스트를 작성하려는데 decreaseStock 메서드가 너무 길었다. 약 40라인이다. 15라인 제한을 한참 넘는다.

테스트를 먼저 작성하고 리팩토링하는 방법도 있지만, 너무 긴 메서드는 테스트하기도 어렵다. 솔직히 무엇을 테스트해야 하는지 파악하기 힘들다. 그래서 그냥 리팩토링을 먼저 하기로 했다.

decreaseStock의 로직을 분석했다. 크게 세 부분이다. 프로모션 재고 차감, 일반 재고 차감, productMap 재구성. 이걸 메서드로 각각 분리했다.

```typescript
decreaseStock(productName: string, quantity: number, promotion: Promotion | null): void {
  let remaining = quantity

  if (promotion) {
    remaining = this.decreasePromotionStock(productName, remaining, promotion)
  }

  if (remaining > 0) {
    this.decreaseNormalStock(productName, remaining)
  }

  this.productMap = this.groupByName(this.products)
}
```

메인 메서드는 15라인 이하가 되었다. 하지만 private 메서드인 decreasePromotionStock과 decreaseNormalStock이 각각 20라인 정도였다. 이것도 15라인을 넘는다.

더 쪼개야 했다. Product 인스턴스를 찾는 부분을 findPromotionProductIndex와 findNormalProductIndex로 분리했다. Product를 새로 만들어서 교체하는 부분을 updateProductQuantity로 분리했다.

최종적으로 5개 메서드로 나눴고, 모두 15라인 이하가 됐다. 처음에는 메서드가 너무 많아지는 게 아닌가 (15라인 이하에 강박을 두고있나) 걱정했는데, 오히려 각 메서드의 책임이 명확해졌다.

## 축약 변수명 제거

리팩토링하면서 또 발견한 문제가 있었다. 화살표 함수에서 p를 쓰고 있었다.

```typescript
const activePromotions = promotions.filter((p) => p.isActive())
```

p가 promotion을 의미한다는 건 알지만, 명확하게 쓰는 게 맞다.

```typescript
const activePromotions = promotions.filter((promotion) => promotion.isActive())
```

더 길어지긴 했지만 명확하다. 코드를 읽는 사람이 추론할 필요가 없다.
Inventory뿐만 아니라 PromotionPolicy에도 p가 있었다. 전부 promotion이나 product로 바꿨다.

## TypeScript 에러 해결

리팩토링 후 TypeScript 에러가 났다. this.products[index]가 possibly undefined라는 경고였다. findIndex가 -1을 반환하면 배열 접근이 undefined일 수 있다.

원래 코드에서는 한 곳에서 체크했는데, 메서드를 분리하면서 여러 곳에서 배열 접근이 생겼다. 각 위치에 undefined 체크를 추가했다.

```typescript
const promoProduct = this.products[promoIndex]
if (!promoProduct) {
  return quantity
}
```

TypeScript 컴파일러가 가능한 모든 경우를 체크하게 만드는 게 중요하다. 런타임 에러를 방지할 수 있다.

## Inventory 테스트 작성

리팩토링이 끝나고 테스트를 작성했다. 14개 테스트를 만들었다. findByName, getPromotionStock, getNormalStock, validateStock, decreaseStock 같은 핵심 메서드들을 검증했다.

특히 decreaseStock 테스트가 중요했다. 프로모션 재고 우선 차감이 제대로 작동하는지, 프로모션 재고가 부족하면 일반 재고를 쓰는지, 프로모션이 없으면 일반 재고만 차감하는지 확인했다.

리팩토링 덕분에 테스트 작성이 쉬웠다. 각 메서드가 하는 일이 명확해서 무엇을 검증해야 하는지 바로 보였다. 메서드가 너무 길면 테스트도 복잡해진다는 걸 느꼈다.

---

이전에 로또에서는 beforeEach를 최대한 지양했다. 각 테스트가 완전히 독립적이어야 한다고 생각했다. 하지만 오늘 불변 객체는 beforeEach로 만들어도 문제없다는 걸 깨달았다. 오히려 중복이 줄어들고 가독성이 좋아진다.

생성자 테스트에 대한 생각도 바뀌었다. JavaScript에서는 의미가 있지만, TypeScript에서는 타입 시스템이 이미 많은 걸 보장한다. 런타임에 검증할 필요가 있는 비즈니스 로직에 집중하는 게 맞다.

오늘 테스트를 작성하면서 요구사항의 의미를 좀 더 이해하게 됐다. 15라인 제한, 축약 금지, 한 메서드 한 가지 기능. 처음에는 귀찮은 규칙이라고 생각했는데, 실제로 지키려고 하니까 코드 품질이 올라갔다.

리팩토링과 테스트를 동시에 진행하면서, 테스트가 있으니까 리팩토링이 안전하다는 걸 체감했다. 메서드를 분리하고 변수명을 바꿔도 테스트가 통과하면 로직이 깨지지 않았다는 확신이 든다.
