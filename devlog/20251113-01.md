# 2025-11-13 (10일차) - 재고 차감 로직 구현

## 재고가 줄어들지 않는 문제

이제는 사용자가 상품을 담고, 결제하고, 영수증을 확인하는 전체 플로우가 작동한다. 그런데 아직 구현이 안된 중요한 한가지가 있다.

재고가 줄어들지 않는다.

콜라를 10개 구매해도 재고는 여전히 10개이다. 다시 페이지를 새로고침하면 재고가 원래대로 돌아온다. 데이터가 CSV에서 로드되기 때문에 새로고침하면 초기화되는 건 당연하지만, 그 전에 구매한 만큼 재고가 차감되는 로직 자체가 없었다.

결제가 된다는 건 재고가 실제로 줄어들어야 한다는 뜻이다. 이건 편의점 POS 시스템의 핵심 기능이다. 정작 지금까지 계산만 하고 실제 재고 변경은 안 하고 있었다는 걸 깨달았다.

## 어디에 재고 차감 로직을 둘 것인가

당연히 재고를 관리하는 건 Inventory의 책임이다. 그래서 Inventory에 `decreaseStock` 메서드를 추가하기로 했다.

Cart에서 결제가 일어나면 Cart가 가진 각 아이템의 수량만큼 Inventory에게 재고를 줄이라고 요청하는 구조다. Cart는 Inventory의 참조를 가지고 있으니 가능하다.

```typescript
// Inventory.ts
decreaseStock(productName: string, quantity: number, promotion: Promotion | null): void
```

이 메서드는 상품명, 수량, 프로모션 정보를 받는다. 왜 프로모션 정보가 필요한가?

## 프로모션 재고를 우선 차감해야 한다

편의점에는 같은 상품이 두 종류로 존재할 수 있다. 프로모션 재고와 일반 재고다.

예를 들어 콜라가 프로모션 재고 10개, 일반 재고 10개 있다고 하자. 사용자가 콜라 12개를 구매했다.
이때 프로모션 재고를 먼저 차감해야 한다. 즉, 프로모션 재고 10개를 전부 쓰고, 나머지 2개는 일반 재고에서 가져온다. 그래야 프로모션 혜택을 최대한 적용할 수 있다.

이 로직을 구현하기 위해 프로모션 정보가 필요했다.

## decreaseStock 구현

```typescript
decreaseStock(productName: string, quantity: number, promotion: Promotion | null): void {
  let remaining = quantity

  if (promotion) {
    const promoIndex = this.products.findIndex(p =>
      p.name === productName && p.hasPromotion() && p.promotion === promotion.name
    )

    if (promoIndex !== -1 && this.products[promoIndex]) {
      const promoProduct = this.products[promoIndex]
      const deductAmount = Math.min(remaining, promoProduct.quantity)

      this.products[promoIndex] = new Product(
        promoProduct.name,
        promoProduct.price,
        promoProduct.quantity - deductAmount,
        promoProduct.promotion
      )

      remaining -= deductAmount
    }
  }

  if (remaining > 0) {
    const normalIndex = this.products.findIndex(p =>
      p.name === productName && !p.hasPromotion()
    )

    if (normalIndex !== -1 && this.products[normalIndex]) {
      const normalProduct = this.products[normalIndex]

      this.products[normalIndex] = new Product(
        normalProduct.name,
        normalProduct.price,
        normalProduct.quantity - remaining,
        normalProduct.promotion
      )
    }
  }

  this.productMap = this.groupByName(this.products)
}
```

로직은 이렇다.

1. 남은 수량을 `remaining` 변수로 추적한다.
2. 프로모션이 있으면 프로모션 재고를 찾는다.
3. 프로모션 재고에서 최대한 차감한다. `Math.min(remaining, promoProduct.quantity)`로 재고보다 많이 차감하지 않게 한다.
4. 프로모션 재고로 부족하면 `remaining`에 남은 수량이 있다.
5. 일반 재고를 찾아서 나머지를 차감한다.
6. 마지막으로 `productMap`을 재구성한다. products 배열이 바뀌었으니까.

## Product 불변성 유지하기

여기서 중요한 부분은 Product를 직접 수정하지 않는다는 것이다.

```typescript
this.products[promoIndex] = new Product(...)
```

기존 Product의 quantity를 바꾸는 게 아니라, 새로운 Product 인스턴스를 만들어서 배열에 교체한다.

Product는 불변 객체로 설계했기 때문이다. readonly 프로퍼티들을 가지고 있다. 만약 `promoProduct.quantity -= deductAmount` 같은 코드를 쓰면 TypeScript가 에러를 낸다.

불변성을 유지하면 예측 가능한 코드가 된다. Product 인스턴스가 생성된 이후로 절대 바뀌지 않는다는 보장이 있으면 디버깅이 쉽다.

## readonly를 제거해야 했다

근데 문제가 하나 있었다.

Inventory의 `products`와 `productMap`이 `readonly`로 선언되어 있었다.

```typescript
private readonly products: Product[]
private readonly productMap: Map<string, Product[]>
```

readonly는 재할당을 막는다. `this.products = ...` 같은 코드를 못 쓴다. 그런데 배열 요소를 교체하는 건 괜찮다. `this.products[0] = ...`는 배열 자체를 재할당하는 게 아니니까.

그런데 `productMap`을 재구성하려면 `this.productMap = this.groupByName(this.products)`를 해야 한다. 이건 재할당이다.

결국 readonly를 제거했다.

```typescript
private products: Product[]
private productMap: Map<string, Product[]>
```

Inventory 입장에서 products는 외부로 노출되지 않는다. private이다. 내부에서만 관리하면 된다. readonly를 포기해도 캡슐화는 유지된다.

## Cart에 checkout 메서드 추가

Inventory에 재고 차감 메서드를 만들었으니 이제 Cart에서 호출해야 한다.

```typescript
checkout(): void {
  this.getItems().forEach((item) => {
    this.inventory.decreaseStock(item.product.name, item.quantity, item.promotion)
  })
}
```

Cart의 모든 아이템을 순회하면서 Inventory의 decreaseStock을 호출한다. 각 아이템의 상품명, 수량, 프로모션을 넘긴다.

간단하다. Cart는 "결제한다"는 책임만 가진다. 실제 재고를 어떻게 줄이는지는 Inventory가 알아서 한다.

## cartStore에 checkout 연결

Cart에 checkout이 생겼으니 cartStore에도 노출해야 한다.

```typescript
const checkout = () => {
  if (!cart.value) {
    throw new Error(ERROR_MESSAGES.STORE.CART_NOT_INITIALIZED)
  }

  cart.value.checkout()
}
```

다른 액션들과 동일한 패턴이다. null 체크를 하고 Cart 메서드를 호출한다.

return에도 checkout을 추가해서 컴포넌트에서 접근할 수 있게 했다.

## CartSummary에서 호출하기

이제 실제로 checkout을 호출할 차례다.

영수증 확인 버튼을 눌렀을 때다.

```typescript
const handleReceiptClose = () => {
  cartStore.checkout()
  isReceiptOpen.value = false
  cartStore.clear()
  cartStore.setMembership(false)
}
```

`handleReceiptClose`의 제일 첫 줄에 `cartStore.checkout()`을 추가했다.

순서가 중요하다.

1. 재고 차감
2. 모달 닫기
3. 장바구니 비우기
4. 멤버십 해제

재고를 먼저 차감하고 나서 장바구니를 비워야 한다. 장바구니를 먼저 비우면 뭘 차감해야 하는지 정보가 사라진다.

## 왜 결제 버튼이 아니라 영수증 확인 시점인가

이 부분을 고민했다.

재고 차감을 결제 버튼을 누를 때 할 수도 있다. `handleCheckout`에서 `cartStore.checkout()`을 호출하는 것이다.

하지만 영수증 확인 시점에 하기로 했다.

이유는 사용자 경험이다. 영수증은 "구매 확정"의 의미를 가진다. 사용자가 영수증을 보고 확인 버튼을 누르면 그때 거래가 완료된다.

만약 결제 버튼을 누르자마자 재고가 차감된다면? 사용자가 영수증을 보다가 뒤로가기를 누르거나 브라우저를 닫으면? 재고는 이미 줄어들었는데 장바구니는 아직 살아있다. 이상한 상태가 된다.

물론 실제 쇼핑몰에서는 결제 시점에 재고를 예약하고, 취소하면 다시 복구하는 복잡한 로직이 있다. 하지만 지금은 간단하게 "영수증 확인 = 구매 확정"으로 처리했다.

## 전체 플로우 정리

이제 전체 플로우가 완성됐다.

1. 사용자가 상품을 선택하고 장바구니에 담는다.
2. 장바구니에서 멤버십을 선택하고 결제하기를 누른다.
3. 영수증 모달이 나타난다.
4. 사용자가 영수증을 확인하고 확인 버튼을 누른다.
5. 재고가 차감된다.
6. 장바구니가 비워지고 멤버십이 해제된다.
7. 다시 쇼핑할 수 있다.

재고 차감이라는 핵심 기능이 드디어 들어갔다.

---

재고 차감 로직을 구현하면서 책임 배치를 고민했다. Inventory가 재고 관리 책임을 가지고, Cart는 결제 책임을 가진다. Cart는 Inventory에게 재고를 줄이라고 요청만 한다.

프로모션 재고 우선 차감 로직도 자연스럽게 구현됐다. `Math.min`으로 재고를 초과하지 않게 차감하고, 남은 수량은 일반 재고에서 처리한다.

Product의 불변성을 유지하기 위해 새 인스턴스를 만들어서 교체했다. Inventory의 readonly는 제거했지만 private이기 때문에 캡슐화는 유지된다.

재고 차감 타이밍은 영수증 확인 시점으로 결정했다. 사용자가 구매를 확정하는 순간에 실제 재고 변경이 일어나는 게 직관적이다.
이제 편의점 POS 시스템의 핵심 기능이 전부 완성됐다.
