# 2025-11-17~18 - Mermaid 다이어그램 학습

## Mermaid를 알게 된 계기

우테코 프리코스 1, 2, 3주차 기간 동안 다른 사람들의 코드 리뷰를 나름 많이 했었다. 다른 이유는 없고, 미션을 끝내고 나면 다른 사람들이 어떻게 구현했는지 궁금해서 GitHub를 뒤적였다. 같은 문제를 바라보면서 각자 어떻게 다르게 받아들여서 풀어냈는지 보는게 상당히 재미있었고 많이 배웠던 경험이였다.

그러다가 어떤 동기분들은 README에 다이어그램을 그려놓은 걸 발견했다. 클래스 구조를 박스와 화살표로 표현해놨는데, 코드를 읽는 것보다 훨씬 이해하기 쉬웠다. 특히 객체 간의 관계나 메서드 호출 순서 같은 걸 시각적으로 보니까 한눈에 들어왔다. 설명 글만 잔뜩 써놓은 것보다 다이어그램 하나가 훨씬 명확했다.

나도 그렇게 만들면 좋겠다고 생각했다. 지금까지 Product, Cart, Inventory 같은 클래스들을 만들면서 각자의 역할은 명확하게 분리했지만, 전체적인 구조를 한눈에 보기는 어려웠다. 특히 Cart가 PromotionPolicy를 사용하고, PromotionPolicy가 다시 Inventory를 참조하는 식의 의존 관계는 코드를 일일이 읽어봐야만 파악할 수 있었다.

처음엔 피그마나 Draw.io 같은 도구로 다이어그램을 그려서 이미지로 저장하려고 했다. 근데 이건 나중에 코드를 수정하면 다이어그램도 다시 그려야 하는데, 이미지 파일을 매번 수정하는 건 너무 번거로웠다. 게다가 이미지 파일은 Git으로 관리할 때도 차이를 비교하기 어렵다.

그러다가 그때 읽어봤던 PR이 생각나서 다시 들어가서, 마크다운으로 바로 다이어그램을 그릴 수 있는 Mermaid라는 걸 알게 됐다. GitHub에서 자동으로 렌더링해준다고 해서 바로 써보기로 했다. 목표로 했던 구현은 다 끝냈으니 그렇게 새로운 공부를 이틀간 시작하였다.

## 첫 시도와 실패

언제나 그렇듯 공식 문서를 찾아봤다. mermaid.js.org에 들어가니까 엄청나게 많은 다이어그램 종류가 있었다. Flowchart, Sequence Diagram, Class Diagram, State Diagram, ER Diagram, Gantt Chart... 뭘 써야 할지 막막했다.

일단 가장 간단해 보이는 Flowchart부터 시도했다. 공식 문서의 예제를 그대로 복사해서 README.md에 붙여넣었다.

```
graph TD
    A[Start] --> B[Process]
    B --> C[End]
```

이렇게 쓰고 GitHub에 올려봤는데 렌더링이 안 됐다. 코드 블록으로만 보였다. 한참을 찾아보니까 코드 블록의 언어를 mermaid로 지정해야 한다는 걸 알았다. 그냥 백틱 세 개만 쓰면 안 되고, 백틱 뒤에 mermaid를 붙여야 했다.

다시 시도하니까 오? 이번에는 제대로 렌더링됐다. 파란색 박스에 화살표가 그려진 간단한 플로우차트가 나타났다.

## 클래스 다이어그램 학습

내가 필요한 건 클래스 다이어그램이었다. Product, Cart, Inventory 같은 클래스들의 구조와 관계를 보여줘야 했다. 공식 문서의 Class Diagram 섹션을 읽기 시작했다.

기본 문법은 이랬다.

```
classDiagram
    class Product {
        string name
        number price
    }
```

이렇게 쓰면 Product라는 클래스가 name과 price 속성을 가진 걸 표현할 수 있었다. 문서를 더 읽어보니까 속성 아래에 메서드를 추가하면 됐다.

```
classDiagram
    class Product {
        string name
        number price
        hasPromotion() boolean
    }
```

이제 hasPromotion 메서드가 추가됐다. 반환 타입도 함께 표시할 수 있었다.

그다음 문제는 접근 제어자였다. TypeScript에서는 private, public, readonly 같은 키워드를 쓰는데, 문서를 찾아보니 기호로 표현했다.

1. 빼기 기호는 private
2. 더하기 기호는 public
3. 샵 기호는 protected

이걸 속성 앞에 붙이면 되는 것 같다.

```
classDiagram
    class Product {
        -string name
        -number price
        +hasPromotion() boolean
    }
```

이제 name과 price가 private이고, hasPromotion이 public인 게 명확하게 보였다.

## 클래스 관계 표현

클래스 하나만 그리는 건 쉬웠다. 어려운 건 클래스 간의 관계를 표현하는 거였다. Cart는 CartItem을 포함하고, CartItem은 Product를 참조하고, Cart는 Inventory를 사용한다. 이런 관계들을 어떻게 그릴까...

이후 Mermaid 문서에서 Relationship 섹션을 읽었다. 여러 가지 화살표 종류가 있었다.

1. 실선 화살표는 Association
2. 빈 마름모는 Aggregation
3. 찬 마름모는 Composition
4. 점선 화살표는 Dependency

처음에는 이 차이를 이해하지 못했다. UML을 제대로 배운 적이 없어서 Aggregation과 Composition이 정확히 뭐가 다른지 몰랐다. 찾아보니까 생명주기와 관련이 있었다. Composition은 부모가 사라지면 자식도 사라지는 강한 관계고, Aggregation은 독립적으로 존재할 수 있는 약한 관계였다.

내 코드에서 Cart와 CartItem의 관계를 생각해봤다. Cart가 사라지면 CartItem도 의미가 없다. 장바구니 없이 장바구니 항목만 있을 수는 없으니까. 그러면 이건 Composition이다. 하지만 Mermaid 문법이 복잡해 보였다. 일단 간단하게 화살표로만 표현하기로 했다.

```
classDiagram
    Cart --> CartItem
```

이렇게 쓰니까 Cart에서 CartItem으로 화살표가 그려졌다. 화살표 옆에 라벨을 붙일 수도 있었다.

```
classDiagram
    Cart --> CartItem : contains
```

contains라는 라벨이 화살표 옆에 표시됐다. 내 눈에 보기엔 관계가 훨씬 명확해졌다.

## 시퀀스 다이어그램 시작

클래스 다이어그램은 정적인 구조를 보여준다. 각 클래스가 어떤 속성과 메서드를 가졌는지, 어떤 클래스와 관계가 있는지를 보여줬다. 하지만 실제로 코드가 어떻게 동작하는지는 보여주지 못했다.

사용자가 장바구니에 상품을 담을 때 어떤 일이 일어나는지 궁금했다. Cart의 addItem 메서드가 호출되고, 그 안에서 Inventory의 validateStock이 호출되고, PromotionPolicy의 findApplicablePromotion이 호출된다. 이런 호출 순서를 보여주려면 시퀀스 다이어그램이 필요했다.

시퀀스 다이어그램 문서를 읽기 시작했다. 기본 문법은 생각보다 간단했다.

```
sequenceDiagram
    Cart->>Inventory: validateStock()
```

Cart에서 Inventory로 메시지를 보내는 화살표가 그려졌다. 실선 화살표에 화살촉이 달려 있었다. 이게 동기 호출을 의미한다고 했다.

여러 메서드 호출을 순서대로 나열할 수 있었다.

```
sequenceDiagram
    Cart->>Inventory: validateStock()
    Cart->>PromotionPolicy: findApplicablePromotion()
    Cart->>CartItem: new CartItem()
```

이렇게 쓰니까 세 개의 화살표가 위에서 아래로 순서대로 그려졌다. 시간 순서를 표현할 수 있었다.

## 참가자 추가와 반환값

시퀀스 다이어그램에서 가장 헷갈렸던 건 반환값이었다. validateStock을 호출하면 void가 반환되지만, findApplicablePromotion을 호출하면 Promotion 객체가 반환된다. 이걸 어떻게 표현할까?

문서를 읽어보니 점선 화살표로 반환값을 표현할 수 있었다.

```
sequenceDiagram
    Cart->>PromotionPolicy: findApplicablePromotion()
    PromotionPolicy-->>Cart: promotion | null
```

실선 화살표는 메서드 호출이고, 점선 화살표는 반환을 의미했다. 반환값의 타입을 화살표 옆에 적을 수 있었다.

그다음 문제는 참가자 선언이었다. 처음에는 참가자를 따로 선언하지 않고 바로 화살표만 그렸다. 그랬더니 참가자 이름이 화살표에 나타나는 순서대로 배치됐다. 순서를 제어하고 싶으면 먼저 선언해야 했다.

```
sequenceDiagram
    participant User
    participant Cart
    participant Inventory
    participant PromotionPolicy
```

이렇게 선언하면 왼쪽부터 User, Cart, Inventory, PromotionPolicy 순서로 배치됐다. 순서를 바꾸면 다이어그램의 레이아웃도 바뀌었다.

actor 키워드도 있었다. participant 대신 actor를 쓰면 사람 모양 아이콘으로 표시됐다. User는 actor로 표현하는 게 더 직관적이었다.

```
sequenceDiagram
    actor User
    participant Cart
```

## 조건문과 반복문

상품을 담을 때 재고가 부족하면 에러가 발생한다. 즉, 재고가 충분할 때만 담을 수 있다. 이런 조건 분기는 alt와 else를 사용할 수 있었다.
alt는 if문 같은 거고, else는 그대로 else였다.

```
sequenceDiagram
    Cart->>Inventory: validateStock()
    alt 재고 부족
        Inventory-->>Cart: throw Error
    else 재고 충분
        Cart->>CartItem: new CartItem()
    end
```

alt 블록 안에서 조건에 따라 다른 동작을 표현할 수 있었다. end로 블록을 닫아야 했다. 이걸 빼먹으면 에러가 났다.

결제할 때는 장바구니의 모든 상품을 순회하면서 재고를 차감한다. 이런 반복문은 loop로 표현했다.

```
sequenceDiagram
    loop 장바구니의 각 상품
        Cart->>Inventory: decreaseStock()
    end
```

loop 라벨에 반복 조건을 한글로 적었다. 영어로 써도 되고 한글로 써도 된다.

## 노트 추가

다이어그램만 보면 이해하기 어려운 부분이 있었다. 예를 들어 decreaseStock이 호출될 때 프로모션 재고를 먼저 차감한다는 로직이 중요한데, 이게 메서드 이름만으로는 드러나지 않았다.

Note를 추가할 수 있었다.

```
sequenceDiagram
    Cart->>Inventory: decreaseStock()
    Note over Inventory: 프로모션 재고 우선 차감
```

Note over 키워드 뒤에 참가자 이름을 쓰면 그 참가자 위에 노트가 표시됐다. 노란색 박스로 강조되어서 눈에 잘 들어왔다.

두 참가자 사이에 노트를 배치할 수도 있었다.

```
sequenceDiagram
    Note over Cart,Inventory: 재고 검증 및 차감
```

이렇게 쓰면 Cart와 Inventory 사이를 가로지르는 큰 노트가 생겼다.

## 실제 적용하면서 겪은 문제들

도메인 README에 실제로 다이어그램을 그리면서 여러 문제를 겪었다.

첫 번째 문제는 클래스 다이어그램이 너무 복잡해진 것이었다. 6개 클래스를 모두 포함하고, 각 클래스의 모든 속성과 메서드를 나열하니까 다이어그램이 너무 길어졌다. 가독성이 오히려 떨어졌다.

메서드를 줄였다. 각 클래스에서 가장 중요한 메서드 5~6개만 남기고 나머지는 제거했다. private 메서드도 대부분 뺐다. 외부에서 호출되는 public 메서드만 남겼다.

두 번째 문제는 화살표 방향이었다. Cart가 PromotionPolicy를 사용한다는 걸 표현하려고 Cart --> PromotionPolicy로 화살표를 그렸다. 그런데 자꾸 헷갈렸다. 화살표가 의존 방향을 나타내는지, 데이터 흐름을 나타내는지 애매했다.

UML 관례를 찾아봤다. 화살표는 의존 방향을 나타낸다고 했다. Cart가 PromotionPolicy를 알고 있으면 Cart --> PromotionPolicy가 맞았다. 반대로 그리면 의미가 바뀐다.

세 번째 문제는 화살표 종류였다. 처음에 모든 관계를 실선 화살표로 그렸다. 그랬더니 포함 관계인지 참조 관계인지 구분이 안 됐다. Cart와 CartItem은 포함 관계지만, Cart와 PromotionPolicy는 단순 참조 관계다.

라벨을 추가했다. contains, uses, manages, references 같은 동사를 화살표 옆에 적으니까 관계가 명확해졌다. 화살표 종류를 바꾸는 것보다 라벨을 추가하는 게 더 직관적이었다.

## 시퀀스 다이어그램 레이아웃

세 개의 시퀀스 다이어그램을 그렸다. 상품 담기, 프로모션 확인, 결제 및 재고 차감. 각각 다른 시나리오를 표현했다.

처음에는 모든 상황을 하나의 다이어그램에 담으려고 했다. 상품을 담고, 프로모션을 확인하고, 결제하는 전체 플로우를 하나로 그렸다. 그랬더니 다이어그램이 너무 길어져서 스크롤을 한참 내려야 했다.

다이어그램을 분리했다. 각 시나리오별로 독립적인 다이어그램을 만들었다. 이게 훨씬 이해하기 쉬웠다. 각 다이어그램이 하나의 명확한 스토리를 가졌다.

상품 담기 다이어그램에서는 재고 검증과 프로모션 적용에 집중했다. 프로모션 확인 다이어그램에서는 추가 증정 가능 여부를 계산하는 로직을 보여줬다. 결제 다이어그램에서는 재고 차감의 우선순위를 표현했다.

## 타입 표기법

TypeScript의 타입을 Mermaid에서 어떻게 표현할지 고민했다. Map<string, CartItem>이나 Promotion | null 같은 복잡한 타입을 그대로 쓸 수 있을까 궁금했다.

일단 시도해봤다. 제너릭도 되고, 유니온 타입도 되었다.

```
classDiagram
    class Cart {
        -Map~string,CartItem~ items
        -Promotion|null promotion
    }
```

제너릭은 꺾쇠 대신 물결표를 사용했다. 꺾쇠는 Mermaid 문법과 충돌할 수 있어서 물결표로 대체했다. 유니온 타입은 그대로 파이프 기호를 쓸 수 있었다.

배열은 대괄호로 표현했다.

```
classDiagram
    class Inventory {
        -Product[] products
    }
```

TypeScript 코드와 거의 똑같이 쓸 수 있었다. 코드를 보고 다이어그램을 만들 때 타입을 옮겨 적기만 하면 됐다.

## 메서드 파라미터

메서드 시그니처를 어디까지 상세하게 표현할지 고민했다. addItem(product: Product, quantity: number)처럼 파라미터까지 다 적을까, 아니면 addItem()처럼 간단하게 적을까?

처음에는 파라미터를 모두 적었다. 정확한 정보를 제공하고 싶었다. 하지만 다이어그램이 너무 복잡해졌다. 메서드 이름이 길어지면서 박스 크기가 커지고, 전체 레이아웃이 흐트러졌다.

결국엔 중요한 메서드만 파라미터를 적고, 나머지는 괄호만 남겼다. addItem이나 validateStock처럼 핵심 메서드는 파라미터를 명시하고, getTotalPrice나 isEmpty 같은 단순한 메서드는 괄호만 적었다. 타협점을 찾았다!

반환 타입은 거의 모든 메서드에 적었다. void인지 number인지 boolean인지는 메서드의 역할을 이해하는 데 중요했다.

## GitHub에서 확인

로컬에서는 vscode 확장 프로그램을 깔아서 마크다운 미리보기로 확인했지만, GitHub에서 어떻게 보일지 궁금했다.

다행히 모든 다이어그램이 제대로 렌더링됐다. 클래스 다이어그램은 파란색과 초록색으로 깔끔하게 그려졌다. 시퀀스 다이어그램은 회색 배경에 화살표가 선명하게 보였다.

한 가지 아쉬운 점은 다이어그램 스타일을 커스터마이즈할 수 없다는 것이었다. 색상이나 폰트를 바꾸고 싶었지만, Mermaid는 기본 테마만 제공했다. 테마를 바꿀 수는 있지만, GitHub에서는 적용되지 않았다.

그래도 기본 스타일도 충분히 깔끔했다. 무엇보다 텍스트로 관리할 수 있다는 게 큰 장점이었다. 나중에 클래스를 수정하면 마크다운 파일도 함께 수정하면 된다. Git diff로 변경 사항을 비교할 수도 있다.

## 배운 점

Mermaid를 처음 써봤지만 생각보다 쉽게 익힐 수 있었다. 공식 문서가 잘 되어 있어서 예제를 따라 하면서 배울 수 있었다. 복잡한 UML 도구를 배우는 것보다 훨씬 빨랐다.

클래스 다이어그램은 정적인 구조를 보여주는 데 유용했다. 각 클래스가 무엇을 가지고 있고, 어떤 관계를 맺고 있는지를 한눈에 볼 수 있었다. 코드를 모르는 사람도 다이어그램만 보고 전체 구조를 이해할 수 있다.

시퀀스 다이어그램은 동적인 흐름을 보여주는 데 좋았다. 메서드 호출 순서, 조건 분기, 반복 로직을 시각적으로 표현할 수 있었다. 특히 복잡한 비즈니스 로직을 설명할 때 유용했다. 말로 설명하면 길어지는 걸 다이어그램 하나로 정리할 수 있었다.

다만 다이어그램을 너무 상세하게 그리면 오히려 가독성이 떨어진다는 걸 배웠다. 모든 메서드를 다 적을 필요는 없다. 중요한 것만 선택해서 보여주는 게 더 효과적이다. 다이어그램의 목적은 이해를 돕는 거지, 코드를 완벽하게 재현하는 게 아니다.

앞으로 다른 프로젝트에서도 Mermaid를 쓸 것 같다. 특히 복잡한 시스템을 설명할 때 유용할 것 같다. 아키텍처 문서나 설계 문서에 다이어그램을 추가하면 이해도가 크게 높아질 것이다.
