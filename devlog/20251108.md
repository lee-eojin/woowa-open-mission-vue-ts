# 2025-11-08 (5일차)

## 구현보다 학습에 집중한 날

오늘은 기능을 많이 만들기보다 Vue의 핵심 개념들을 제대로 이해하는 데 시간을 썼다. 지난 며칠간 도메인 클래스들을 열심히 만들었는데, 정작 Vue 컴포넌트 설계 방법에 대해서는 깊이 생각해본 적이 없었다는 생각이 들었다. 간단한 컴포넌트 하나를 만들면서 Vue 공식 문서를 정독하고, TypeScript와 함께 사용하는 패턴을 공부하기로 했다.

## 왜 모달부터 시작했나

프로젝트에 필요한 컴포넌트는 많지만, 그중에서도 모달을 먼저 만들기로 했다. 모달은 재사용성이 중요한 컴포넌트다. 프로모션 추가 확인, 정가 결제 확인, 추가 구매 안내 등 여러 곳에서 쓰일 텐데, 매번 새로 만들 수는 없으니까.

그리고 모달은 Props, Emit, Slot, Teleport 같은 Vue의 핵심 기능들이 다 들어간다. 하나의 컴포넌트로 여러 개념을 동시에 학습할 수 있어서 학습 효율이 좋을 것 같았다.

## Vue 컴포넌트 설계 원칙 학습

본격적으로 코드를 쓰기 전에 Vue 공식 문서의 컴포넌트 섹션을 정독했다. 특히 재사용 가능한 컴포넌트를 어떻게 설계해야 하는지에 대한 부분이 인상적이었다.

공식 문서에서 강조하는 핵심은 단일 책임 원칙이었다. 컴포넌트는 한 가지 일만 잘해야 하고, 재사용 가능하려면 특정 비즈니스 로직에 의존하면 안 된다는 것이다. 도메인 클래스를 설계할 때 적용했던 원칙이 컴포넌트에도 똑같이 적용되는 셈이다.

모달의 경우 열고 닫는 것만 책임지고, 내부에 무엇을 보여줄지는 부모 컴포넌트가 결정하게 해야 한다. 그래서 Slot이 필요하다는 걸 이해했다.

## Props 타입 정의 방법 깊이 파기

Vue 3 + TypeScript 조합에서 Props를 타입 안전하게 정의하는 방법을 찾아봤다. 블로그 글도 여러 개 읽고, 공식 문서도 다시 정독했다.

크게 세 가지 방법이 있었다.

첫 번째는 런타임 Props를 사용하는 방법이다. defineProps에 객체를 넘겨서 type, required, default를 지정하는 방식인데, JavaScript와 비슷해서 익숙하긴 한데 TypeScript의 장점을 제대로 못 살린다는 느낌이었다.

두 번째는 타입 기반 Props다. interface를 정의하고 defineProps에 제네릭으로 넘기는 방식이다. 타입 안전성은 확보되지만 기본값을 설정하기가 까다로웠다.

세 번째는 withDefaults를 사용하는 방법이다. 타입 기반 Props에 withDefaults를 조합하면 타입 안전성과 기본값 설정을 동시에 할 수 있다. 공식 문서에서도 이 방식을 권장하고 있어서 이걸로 결정했다.

```typescript
interface Props {
  isOpen: boolean
  title?: string
  closeOnBackdrop?: boolean
  closeOnEsc?: boolean
}

const props = withDefaults(defineProps<Props>(), {
  title: '',
  closeOnBackdrop: true,
  closeOnEsc: true,
})
```

isOpen은 필수 prop이라서 기본값이 없고, 나머지는 선택 사항이라 기본값을 제공한다. TypeScript 컴파일러가 필수 prop을 빠뜨리면 에러를 내주니까 안전하다.

## Emit 타입 정의와 이벤트 설계

Props는 부모에서 자식으로 데이터를 전달하는 것이고, Emit은 자식이 부모에게 이벤트를 알리는 방법이다. Vue의 단방향 데이터 흐름을 유지하려면 Emit을 제대로 써야 한다.

TypeScript에서는 Emit도 타입을 정의할 수 있다. interface 형태로 각 이벤트의 이름과 매개변수 타입을 명시한다.

```typescript
interface Emits {
  (e: 'close'): void
}

const emit = defineEmits<Emits>()
```

모달은 close 이벤트만 발생시킨다. 매개변수가 없으니 void다. 나중에 확인/취소를 구분해야 하면 'confirm', 'cancel' 이벤트를 추가할 수도 있겠지만, 지금은 단순하게 유지했다.

## Teleport 원리 이해하기

Teleport는 처음 들어보는 개념이라 공식 문서를 여러 번 읽었다. 컴포넌트가 논리적으로는 특정 부모 안에 있지만, 실제 DOM에서는 다른 위치에 렌더링되게 해주는 기능이다.

왜 필요한지 처음엔 이해가 안 됐는데, z-index 문제를 알고 나서 이해됐다. 모달은 화면 전체를 덮는 오버레이가 필요한데, 만약 깊게 중첩된 컴포넌트 안에서 모달을 만들면 부모 컴포넌트들의 overflow나 z-index에 영향을 받을 수 있다.

Teleport를 쓰면 컴포넌트 트리 구조는 유지하면서 실제 렌더링은 body 바로 아래에 할 수 있다. 이렇게 하면 CSS 스타일 간섭을 받지 않고 항상 최상단에 표시된다.

```vue
<Teleport to="body" v-if="isOpen">
  <!-- 모달 내용 -->
</Teleport>
```

v-if를 Teleport에 바로 붙이면 isOpen이 false일 때는 Teleport 자체가 실행되지 않아서 성능상 유리하다는 것도 배웠다.

## Slot으로 재사용성 확보하기

Slot은 컴포넌트에 구멍을 뚫어놓는 것이라고 이해했다. 부모 컴포넌트가 원하는 내용을 그 구멍에 채워 넣을 수 있다.

모달에는 두 가지 Slot을 만들었다. 기본 슬롯은 모달 본문 내용이 들어갈 자리고, footer라는 이름을 가진 named slot은 버튼 영역이다.

기본 슬롯은 항상 있어야 하지만, footer는 선택 사항이다. 어떤 모달은 확인 버튼만 있고, 어떤 모달은 확인/취소 두 개가 있고, 어떤 모달은 아예 버튼이 없을 수도 있다.

```vue
<div class="modal-body">
  <slot />
</div>

<div v-if="$slots.footer" class="modal-footer">
  <slot name="footer" />
</div>
```

`$slots.footer`로 footer 슬롯에 내용이 전달됐는지 확인하고, 있을 때만 footer 영역을 렌더링한다. 이렇게 하면 버튼이 필요 없는 모달에서는 footer가 아예 나타나지 않는다.

사용하는 쪽에서는 이렇게 쓴다.

```vue
<BaseModal :is-open="isModalOpen" title="프로모션 안내" @close="closeModal">
  <p>현재 1+1 프로모션이 적용 가능한 상품입니다.</p>

  <template #footer>
    <button @click="closeModal">취소</button>
    <button @click="confirm">확인</button>
  </template>
</BaseModal>
```

같은 BaseModal 컴포넌트로 다양한 모달을 만들 수 있게 됐다.

## 라이프사이클 훅 학습

ESC 키를 눌렀을 때 모달을 닫는 기능을 추가하려면 키보드 이벤트 리스너를 등록해야 한다. 그런데 이벤트 리스너를 언제 등록하고 언제 제거해야 하는지 고민이 됐다.

Vue 공식 문서의 라이프사이클 훅 섹션을 읽었다. Composition API에서는 onMounted, onUnmounted 같은 함수로 라이프사이클을 다룬다.

onMounted는 컴포넌트가 DOM에 마운트된 직후에 실행되고, onUnmounted는 컴포넌트가 제거되기 직전에 실행된다. 이벤트 리스너는 onMounted에서 등록하고 onUnmounted에서 제거하는 게 정석이다.

```typescript
const handleEscKey = (event: KeyboardEvent) => {
  if (event.key === 'Escape' && props.closeOnEsc && props.isOpen) {
    emit('close')
  }
}

onMounted(() => {
  document.addEventListener('keydown', handleEscKey)
})

onUnmounted(() => {
  document.removeEventListener('keydown', handleEscKey)
})
```

처음에는 왜 제거를 해야 하는지 의문이었는데, 메모리 누수 방지를 위해서라는 걸 알았다. 이벤트 리스너를 등록만 하고 제거하지 않으면 컴포넌트가 사라진 뒤에도 리스너가 메모리에 남아있다. 모달을 여러 번 열고 닫다 보면 리스너가 계속 쌓여서 성능 문제가 생길 수 있다.

Options API의 created, destroyed와 비교하면서 공부했는데, Composition API가 훨씬 직관적이고 타입 안전성도 좋다는 느낌을 받았다.

## Transition 애니메이션 적용

모달이 갑자기 나타나고 사라지면 사용자 경험이 좋지 않다. 부드러운 페이드 인/아웃 효과를 주고 싶었다.

Vue의 Transition 컴포넌트를 사용하면 CSS 트랜지션을 쉽게 적용할 수 있다. v-enter-from, v-enter-active, v-enter-to, v-leave-from, v-leave-active, v-leave-to 클래스를 자동으로 추가해준다.

```vue
<Transition name="modal" appear>
  <div class="modal-overlay">
    <!-- 내용 -->
  </div>
</Transition>
```

name을 modal로 지정하면 modal-enter-from, modal-enter-active 같은 클래스가 생성된다. CSS에서 이 클래스들의 스타일을 정의하면 된다.

appear 속성은 처음 렌더링될 때도 트랜지션을 적용하는 옵션이다. 이게 없으면 모달이 처음 열릴 때는 애니메이션 없이 나타나고, 두 번째부터만 애니메이션이 적용된다.

공식 문서의 Transition 섹션에서 여러 예제를 보면서 fade, slide, scale 같은 효과를 어떻게 만드는지 공부했다. 우리 모달은 opacity 변화와 약간의 scale 효과를 조합했다.

## 템플릿 구조 최적화 고민

처음 만들었을 때 템플릿이 이렇게 생겼다.

```vue
<Teleport to="body"></Teleport>
```

Teleport 안에 Transition이 있고, 그 안에 v-if가 있고, 그 안에 실제 모달 내용이 있다. 들여쓰기가 6단계까지 들어가니 코드가 너무 오른쪽으로 밀린다.

v-if의 위치를 고민했다. Transition 안에 있어야 할까, Teleport에 있어야 할까?

성능 관점에서 생각해봤다. v-if가 Teleport에 있으면 isOpen이 false일 때 Teleport 자체가 실행되지 않는다. 반면 v-if가 안쪽에 있으면 Teleport는 실행되는데 내부 요소만 렌더링되지 않는다.

결국 v-if를 Teleport로 올렸다. 들여쓰기도 한 단계 줄고, 성능도 약간 개선되는 일석이조다.

```vue
<Teleport to="body" v-if="isOpen"></Teleport>
```

## 배운 점

오늘은 코드는 별로 안 만들었지만 Vue의 핵심 개념들을 제대로 이해하는 시간이었다.

Props와 Emit으로 부모-자식 컴포넌트가 어떻게 통신하는지, 단방향 데이터 흐름이 왜 중요한지 알게 됐다. Slot으로 컴포넌트를 재사용 가능하게 만드는 방법도 이해했다. Teleport라는 새로운 개념도 배웠고, Transition으로 사용자 경험을 개선하는 방법도 익혔다.

TypeScript와 조합했을 때 withDefaults, interface, 제네릭을 어떻게 활용하는지도 배웠다. 타입 안전성을 유지하면서도 유연한 컴포넌트를 만들 수 있다는 게 인상적이었다.

라이프사이클 훅으로 메모리 누수를 방지하는 것처럼, 단순히 작동만 하는 코드가 아니라 제대로 된 코드를 작성하는 방법을 배웠다.

객체지향 설계 원칙이 컴포넌트 설계에도 똑같이 적용된다는 것도 깨달았다. 단일 책임, 재사용성, 의존성 분리 같은 원칙들이 도메인 클래스뿐만 아니라 UI 컴포넌트에도 중요하다.
