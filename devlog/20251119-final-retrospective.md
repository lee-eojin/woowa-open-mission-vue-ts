# 2025-11-19 - 최종 회고

드디어 내 아이디어를 구현해보는 것을 홀로 해봐서그런지 재밌었지만 최근에 가장 하드한 2주가 아니였나 싶다.

우테코 프리코스 8기 1, 2, 3주차가 끝나고 오픈미션을 시작한 지 2주가 지났다. 7기 편의점 미션을 가져와서 Vue.js와 TypeScript로 재구현하겠다고 결심한 순간부터 지금까지, 생각보다 많은 걸 배웠고 예상하지 못한 곳에서 많은 걸 고민했다. 처음에 이 프로젝트를 시작한 이유는 단순했다. 프리코스 3주 동안 JavaScript로만 코딩하면서 프론트엔드 프레임워크에 대한 갈증이 생겼다. 콘솔 입출력으로만 동작하는 프로그램을 만들면서 실제 사용자가 쓸 수 있는 UI를 만들어 볼 수 있는 기회가 있으면 얼마나 좋을까 생각했었다.

그러던 로또 미션 마무리 즈음, 4주차에 오픈미션이라는 게 있다는 소식을 들었다. 오픈미션이 무엇일지는 8기 지원자 동료분들 모두가 몰랐었다. 오픈 미션을 들어보니 미션을 자유롭게 정해서 원하는 방식으로 재구현할 수 있는 기회라고 생각했다. 그러다가 7기 편의점 미션을 보자마자 바로 이거다 싶었다. 프론트엔드 프레임워크로 웹 UI를 만들어보고 싶었는데, 비즈니스 로직은 이미 콘솔 미션으로 익숙했다. 처음에는 타이밍이 딱 맞아떨어졌다고 생각한게, 도메인 설계만 잘하면 UI를 바꾸는 건 그렇게 어렵지 않을 것 같았다. 처음에는... 하하하...

---

Vue와 TypeScript를 결합해서 프로젝트를 만들기로 결심했다. 처음에는 React를 선택할까 고민했다. 사실 취업 시장, 그리고 현업에서 React 수요가 더 많다는 건 알고 있었다. 하지만 프리코스 기간이 끝나고 바로 시작하는 프로젝트라서 빠르게 결과물을 만들고 싶었다. React의 JSX 문법이나 Hook 개념은 익숙하지 않았고, 학습 곡선이 가파를 것 같았다. Vue는 HTML 기반 템플릿이라서 직관적이었고, 공식 문서가 한글로 잘 되어 있어서 접근성이 좋았다. Composition API라는 게 있다는 걸 알았고, 이게 React Hook과 비슷하면서도 더 명시적이라는 평을 봤다. 2주 안에 프로젝트를 완성하려면 Vue가 더 나은 선택이라고 판단했다.

그렇게 11월 4일에 오픈미션이 시작되자마자 빠르게 결정하고 프로젝트를 시작했다. Vite로 Vue 프로젝트를 생성하고 TypeScript를 설정하는 것부터 시작했다. create-vue를 사용하니까 기본 구조가 다 세팅되어 있었다. ESLint, Prettier, Vitest까지 한 번에 설정되었다. Vue의 장점인것같다. 별도로 설정 파일을 만지작거릴 필요 없이 바로 코딩을 시작할 수 있었다.

일단 원작 미션에 있는 데이터를 살펴보았다. 그러다보니 자연스럽게 첫 번째 작업은 데이터 파싱이었다. products.md와 promotions.md 파일을 읽어서 Product와 Promotion 객체로 만들어야 했다. CSV 형식이라서 파싱 로직이 필요했다. 처음에는 함수로 만들었다. parseCsv, parseProducts, parsePromotions 이런 식으로 분리했다. 동작은 했지만 뭔가 깔끔하지 않았다. 함수들이 흩어져 있고, 관련 있는 로직들이 응집되지 않았다. 클래스로 만들면 어떨까 생각했다. CsvParser 클래스를 만들고, ProductParser와 PromotionParser가 이걸 사용하는 구조로 바꿨다. 각 파서가 검증 로직도 포함하게 했다. 가격이 음수면 에러를 던지고, 날짜 형식이 잘못되면 에러를 던지는 식으로 만들었다. 클래스로 만들고 나니까 책임이 명확해졌다. ProductParser는 상품 파싱과 검증만 책임진다. 다른 곳에서 이 로직을 재사용하기도 쉬웠다.

데이터를 불러오는 것까지 해결했으니 이제 본격적으로 도메인 클래스를 설계할 차례였다. 사실 이 과정이 3주간 우테코를하면서 가장 많이 고민했던 기억이 있기에, 더 유기적이고 객체지향적으로 설계하고자 노력했다. Product, Promotion, CartItem, Cart, Inventory, PromotionPolicy 여섯 개를 만들었다. 프리코스 기간 동안 단일 책임 원칙, 캡슐화, 불변성 같은 개념을 익혔는데, 결과적으로 돌아보면 실제로 적용하는 건 생각보다 어려웠다. 처음에는 Cart에 모든 로직을 다 넣었다. 재고 검증도 Cart에서 하고, 프로모션 찾기도 Cart에서 하고, 가격 계산도 Cart에서 했다. 그랬더니 Cart 클래스가 엄청나게 길어졌다. 테스트 작성도 어려웠다. Cart를 테스트하려면 Inventory와 Promotion을 다 준비해야 했다.

리팩토링도 수없이 했다. 예를들면 재고 관리를 Inventory로 따로 분리했다. 프로모션 재고와 일반 재고를 구분하는 로직, 재고를 차감하는 로직을 모두 Inventory에 넣었다. 프로모션 정책 판단은 PromotionPolicy로 분리했다. 추가 증정이 가능한지, 정가 결제 수량이 얼마인지 계산하는 로직을 PromotionPolicy에 넣었다. Cart는 이제 이 두 객체를 조합해서 장바구니 기능을 제공한다. Cart가 혼자 다 하는 게 아니라 Inventory에게 재고 검증을 맡기고 PromotionPolicy에게 프로모션 찾기를 맡긴다. 리팩토링 후 Cart는 훨씬 간결해진 것 같고, 각 클래스를 독립적으로 테스트할 수 있게 된 것 같다.

불변성을 유지하는 것도 고민했다. Product 클래스를 readonly로 만들었다. 한번 생성되면 값을 바꿀 수 없다. 재고를 차감할 때는 새로운 Product 인스턴스를 만들어서 배열에 교체한다. 이렇게 하면 의도치 않은 부작용을 방지할 수 있다. Cart의 items도 Map으로 관리하면서 외부에서 직접 수정할 수 없게 했다. getItems 메서드는 배열을 반환하지만, 이건 Map의 복사본이라서 외부에서 수정해도 내부 상태는 변하지 않는다.

도메인 로직을 만들고 나니 이제 화면을 그릴 차례였다. Vue 컴포넌트를 만들 때 처음에는 ProductList에서 모든 걸 다 처리하려고 했다. 상품 목록 표시하고, 각 상품의 수량 입력받고, 담기 버튼 만들고, 프로모션 배지 붙이고. 그랬더니 코드가 엄청 길어지면서 어디가 어딘지 찾기도 힘들어졌다. 한 파일 안에서 스크롤을 한참 내려야 원하는 부분을 찾을 수 있었다. ProductTableRow라는 컴포넌트를 따로 만들었다. 부모에서는 상품 데이터만 넘겨주고, 자식에서는 그걸 받아서 한 줄씩 표시하게 했다. 사용자가 담기 버튼을 누르면 자식이 부모한테 알려준다. 컴포넌트를 쪼개니까 각자 역할이 명확해지고, 코드 찾기도 쉬워졌다. ProductTableRow를 수정할 때 ProductList는 신경 쓸 필요가 없었다.

컴포넌트를 나누다 보니 자연스럽게 전역 상태 관리가 필요해졌다. Cart와 Inventory를 여러 컴포넌트에서 공유해야 했다. Pinia를 사용하기로 했다. Vuex보다 간단하다는 말을 듣고 Pinia를 선택했던 것 같다. cartStore를 만들어서 Cart와 Inventory 인스턴스를 관리했다. computed로 반응형 데이터를 만들고, actions로 도메인 메서드를 호출했다. 여기서 반응성 문제를 겪었다. Inventory를 ref로 감쌌더니 Vue가 내부의 모든 Product 객체까지 반응형으로 만들려고 했다. 재고가 많으면 성능이 떨어졌다. shallowRef로 바꿔서 얕은 반응성만 유지하니까 문제가 해결됐다. 이런 미묘한 차이를 배우는 게 재미있었다.

기본 기능은 돌아가는데 뭐랄까, 사용자 경험 측면에서 뭔가가 좀 부족했다. 프로모션 안내 모달을 만들기로 했다. 사용자가 2+1 상품을 2개만 담으면 1개를 무료로 더 받을 수 있다고 알려줘야 한다. 프로모션 재고가 부족해서 일부는 정가로 결제해야 하면 그것도 알려줘야 한다. PromotionConfirmModal 컴포넌트를 만들어서 두 가지 상황을 처리했다. type prop으로 additional과 fullPrice를 구분했다. 같은 모달 컴포넌트를 재사용하면서 다른 내용을 보여줄 수 있었다.

결제와 영수증 기능을 만들 때는 데이터 흐름을 정리했다. 사용자가 결제 버튼을 누르면 영수증 모달이 뜬다. 영수증에서 확인 버튼을 누르면 그때 실제로 재고가 차감된다. 이 타이밍이 중요했다. 영수증을 보여주는 순간에 재고를 차감하면 사용자가 취소할 방법이 없다. 영수증 확인이 구매 확정 시점이라고 판단했다. checkout 메서드를 호출하면 장바구니의 모든 상품을 순회하면서 Inventory의 decreaseStock을 호출한다. 프로모션 재고를 먼저 차감하고, 부족하면 일반 재고를 차감한다. 이 우선순위가 비즈니스 로직이었다.

멤버십 할인을 구현할 때는 계산 순서를 고민했다. 총 구매액에서 프로모션 할인을 먼저 빼고, 그다음 멤버십 할인을 적용한다. 멤버십 할인은 프로모션 미적용 금액의 30퍼센트다. 최대 8000원까지만 할인된다. Math.min으로 상한선을 적용했다. 이 계산식을 Cart의 getMembershipDiscount 메서드로 캡슐화했다. 외부에서는 이 로직을 몰라도 된다. useMembership 플래그만 전달하면 알아서 계산해준다.

목표로 했던 기능 구현을 다 하고 나니 테스트를 작성해야겠다는 생각이 들었다. 정말이지 분량이 2주차, 3주차와 차원이 다르다보니 어디서부터 시작해야 할지 막막하긴 했었다. Vitest 문법을 배우고, describe와 it을 사용해서 테스트 구조를 만들었다. Product 테스트는 간단했다. hasPromotion이 제대로 동작하는지, getTotalPrice가 정확히 계산하는지 확인하면 됐다. Cart 테스트는 복잡했다. Inventory와 Promotion을 미리 준비해야 했다. Mock 객체를 만들까 고민했지만, 실제 객체를 사용하기로 했다. 통합 테스트에 가까웠지만, 실제 사용 시나리오를 검증할 수 있어서 좋았다. 51개 테스트를 작성했고 모두 통과했다. 테스트를 작성하고 나니까 리팩토링할 때 자신감이 생겼다. 코드를 바꿔도 테스트가 통과하면 동작이 보장된다는 걸 알았다.

기능은 다 만들었는데, 디자인이 좀... 밋밋했었다. 일단 급하게 색상 대비를 높여서 가독성을 올렸다. 영수증과 비슷하게 하려고 회색 텍스트를 처음에 썼었는데 막상 너무 흐려서 잘 안 보였다. 그래서 이런 부분도 색상을 진하게 바꿨다. 테이블 정렬도 조정했다. 가격과 재고는 숫자니까 오른쪽 정렬이 맞다. 프로모션은 중앙 정렬이 보기 좋았다. 장바구니 레이아웃도 개선했다. max-width를 제거하고 width 100퍼센트로 바꿔서 그리드 영역을 꽉 채웠다. CSS 박스 모델, padding과 margin의 차이, width와 max-width의 차이를 실제로 적용하면서 배웠다.

2주가 슬슬 다가왔을때부터는 이렇게 UI 작업까지 마무리하고 나니 프로젝트의 완성도를 더 높이고 싶었다. 문득 프리코스 1, 2, 3주차 기간 동안 다른 사람들의 코드 리뷰를 많이 했었던 게 떠올랐다. 그러다가 어떤 사람들은 README에 다이어그램을 그려놓은 걸 봤다. 클래스 구조를 박스와 화살표로 표현해놨는데, 코드보다 이해하기 쉬웠다. 나도 만들고 싶었다. Mermaid라는 걸 알게 됐다. 마크다운에서 바로 다이어그램을 그릴 수 있었다. 이틀 동안 Mermaid를 공부했다. 클래스 다이어그램과 시퀀스 다이어그램을 그렸다. 클래스 다이어그램으로 정적 구조를 보여주고, 시퀀스 다이어그램으로 메서드 호출 흐름을 보여줬다. 다이어그램을 그리면서 내가 만든 코드를 더 깊이 이해하게 됐다. 어떤 클래스가 어떤 클래스를 의존하는지, 메서드가 어떤 순서로 호출되는지 명확해졌다.

도메인 처리 로직을 글로 정리하는 작업도 했다. 다이어그램만으로는 설명하기 어려운 세부 로직들을 문단 형식으로 풀어서 썼다. 상품을 장바구니에 담는 과정, 프로모션 추가 증정 확인, 정가 결제 수량 계산, 할인 계산, 재고 차감, 객체 간 협력을 각각 자세히 설명했다. 이 과정에서 내 코드를 객관적으로 바라볼 수 있었다. 왜 이렇게 설계했는지, 어떤 의도가 있었는지 다시 생각했다.

---

돌이켜보면 이 프로젝트를 하면서 가장 많이 배운 건 역시나 객체지향 설계였다. 프리코스 기간 동안 단일 책임 원칙, 캡슐화, 불변성 같은 용어들을 많이 들었다. 솔직히 말하면 이론으로만 들으면 와닿지 않았다. "클래스는 하나의 책임만 가져야 한다"는 말이 무슨 뜻인지 머리로는 알았지만, 실제로 코드를 짤 때는 어디까지가 하나의 책임인지 판단하기 어려웠다. 이번 프로젝트를 하면서 그게 조금씩 보이기 시작했다. Cart가 너무 많은 걸 하고 있다는 걸 느낀 순간, 재고 관리는 Inventory가 하면 되겠다고 생각한 순간, 프로모션 정책 판단은 PromotionPolicy가 하면 깔끔하겠다고 판단한 순간들이 있었다. Cart를 만들 때 처음에는 내부에서 new Inventory()를 호출해서 객체를 직접 만들었다. 근데 테스트를 작성하려니까 문제가 생겼다. Cart를 테스트하려면 Inventory의 동작까지 다 확인해야 했다. 그래서 Cart 생성자에서 Inventory를 받게 바꿨다. 외부에서 만들어서 주입하는 방식으로. 이렇게 하니까 테스트할 때 필요하면 가짜 Inventory를 넣을 수도 있었다. 외부에서 Cart의 items를 직접 수정하면 안 될 것 같아서 items를 Map으로 만들고 private으로 숨겼다. getItems 메서드로 복사본만 넘겨줬다. 외부에서 그 복사본을 아무리 수정해도 Cart 내부의 실제 items는 안전했다. 프리코스 때 들었던 용어들이 이제 조금씩 와닿는 것 같다.

타입스크립트를 사용하면서 놀랐던 순간들이 있었다. 함수를 작성할 때 파라미터에 타입을 쓰면 IDE가 자동완성을 해준다. 틀린 타입을 넣으려고 하면 빨간 줄이 그어진다. 코드를 실행하기도 전에 에러를 찾을 수 있었다. 리팩토링할 때 특히 좋았다. 클래스 메서드 시그니처를 바꾸면 그걸 사용하는 모든 곳에서 타입 에러가 났다. 어디를 고쳐야 하는지 IDE가 다 알려줬다. 자바스크립트였으면 실행해봐야 알 수 있는 에러들을 타입스크립트는 코드 작성 중에 잡아줬다. 당분간은 자바스크립트보단 타입스크립트에 빠져버릴지도 모르겠다. 물론 타입을 정의하는 게 번거로울 때도 있었다. 제네릭이나 유니온 타입을 쓸 때는 복잡했다. 하지만 그만큼의 가치는 충분했다.

Vue의 반응형 시스템은 신기했다. cartStore에서 totalPrice를 computed로 만들었다. items가 바뀌면 totalPrice도 자동으로 다시 계산됐다. 내가 따로 "items가 바뀌었으니까 totalPrice도 다시 계산해"라고 명령할 필요가 없었다. 그냥 "totalPrice는 items로부터 이렇게 계산된다"고 선언만 하면 Vue가 알아서 관리해줬다. 장바구니에 상품을 추가하거나 삭제할 때마다 UI의 금액이 자동으로 업데이트됐다. ref와 reactive로 데이터를 감싸기만 하면 Vue가 변화를 감지하고 화면을 새로 그렸다.

---

아쉬운 점도 있었다. 첫째는 컴포넌트 분리가 부족했다. 다시 돌아보니 ProductTableRow가 조금 많은 책임을 가지고 있다. 수량 입력도 받고, 담기 버튼도 있고, 모달도 제어한다. QuantityInput 컴포넌트를 따로 만들면 재사용하기 좋았을 것이다. 둘째는 에러 처리가 부족했다. CSV 파싱이 실패하거나 네트워크 에러가 나면 사용자에게 제대로 알려주지 못한다. try-catch로 에러를 잡아서 사용자 친화적인 메시지를 보여줘야 했다. 셋째는 접근성을 고려하지 못했다. 키보드 네비게이션이 안 되고, 스크린 리더 지원도 안 된다. 시맨틱 HTML을 제대로 쓰지 못했다. 넷째는 반응형 디자인이 없다. 모바일에서는 레이아웃이 깨질 것이다. 미디어 쿼리로 모바일 대응을 했어야 했다고 생각한다.

코드 품질 도구도 더 활용할 수 있었다. ESLint 규칙을 더 엄격하게 설정하거나, SonarQube 같은 정적 분석 도구를 사용할 수도 있었다. 아마도 코드 복잡도를 측정하고, 중복 코드를 찾아내고, 잠재적 버그를 찾을 수 있었을 것이다.

또한 문서화가 약간 부족하지 않았나 싶긴하다. JSDoc으로 각 메서드에 설명을 달면 좋았을 것이다. 파라미터가 무엇을 의미하는지, 반환값이 무엇인지, 어떤 예외가 발생할 수 있는지 명시하면 다른 사람이 코드를 이해하기 쉬웠을 것이다. README도 개발자 관점의 설명만 있고 사용자 관점의 가이드는 없다. 어떻게 사용하는지, 어떤 기능이 있는지 스크린샷과 함께 설명하면 더 좋았을 것이다.

성능 최적화도 고려하면서 나름 공부한다고 하면서 코딩하긴했는데, 만족스럽지는 않다. 상품 목록이 많으면 렌더링이 느릴 수 있다. 가상 스크롤을 사용하거나, 페이지네이션을 추가하면 좋았을 것이다. 이미지 최적화는 하지 못했다. WebP 포맷을 사용하거나, lazy loading을 적용할 수 있었다.

그래도 이 프로젝트를 통해 많이 성장했다. 3주동안 기존의 우테코 방식으로 성장한 것도 큰데, 다른 의미로 성장했다고 생각한다. 가장 우선적으로는 역시나 새로운 기술 스택인 Vue와 TypeScript를 처음 써봤지만 실제로 동작하는 프로덕트를 만들었던 점이지 않을까 싶다. 객체지향 설계를 실제로 적용해봤다. 이외에도 테스트 작성의 중요성을 느껴보고, 상태 관리 라이브러리를 사용해보고, 컴포넌트 기반 개발을 경험해보고, 다이어그램으로 구조를 시각화하는 법도 배웠다. 무엇보다 혼자서 처음부터 끝까지 만들어봤다는 게 좋은 기회지 않았을까? 가장 큰 수확이다.

---

이 프로젝트는 프리코스의 끝이 아니라 우테코의 시작이라고 생각한다. 여기서 배운 걸 바탕으로 더 큰 프로젝트를 만들어보고 싶다. React도 배워보고 싶다. Next.js로 SSR을 구현해보고 싶다. 백엔드도 만들어서 풀스택 프로젝트를 완성하고 싶다. GraphQL도 써보고 싶다. 배포도 제대로 해보고 싶다. CI CD 파이프라인을 구축하고 싶다. 모니터링과 로깅도 설정하고 싶다. (쓰고보니 해보고 싶은게 많네...)

가장 중요한 건 계속 만들어보는 것이라고 생각한다. 튜토리얼만 따라 하는 게 아니라 내 아이디어를 구현해보는 것이다. 실패하고 고민하고 해결하는 과정에서 진짜 배움이 일어난다. 이 프로젝트가 그랬다. 처음에는 막막했지만 하나씩 만들어가면서 자신감이 생겼다. 다음 프로젝트는 더 잘할 수 있을 것 같다.

우테코 프리코스 8기를 통해 코딩의 또 다른 새로운 재미를 다시 느꼈고, 7기 오픈미션을 가져와서 Vue로 재구현하면서 그걸 확장할 수 있었다. 혼자 공부하는 건 조금은 외롭지만, 같은 목표를 가진 사람들과 함께하면 확실히 동기부여가 된다. 8기 동기들의 코드 리뷰를 보면서 많이 배웠고, 내 코드도 발전시킬 수 있었다. 앞으로도 계속 배우고 성장하고 싶다. 코드로 문제를 해결하고, 사용자에게 가치를 제공하는 개발자가 되고 싶다. 이 프로젝트가 그 여정의 한 걸음이었다.
