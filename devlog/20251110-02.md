# 객체지향 관점에서 도메인 클래스 책임 재설계

## 리팩토링 전 문제점 발견

프로모션 판단 로직을 Inventory에 추가한 후 코드를 다시 살펴봤다. 몇 가지 설계 문제가 보였다.

첫째, Inventory가 두 가지 책임을 가지고 있었다. 재고를 관리하면서 동시에 프로모션 정책을 판단한다. canGetAdditionalFreeItem과 calculateFullPriceQuantity 메서드가 그렇다.

둘째, 메서드 시그니처에 문제가 있었다. promotion과 promotions를 매번 파라미터로 받는다. 재고 클래스가 프로모션 정보를 외부에서 계속 받아야 한다.

셋째, Cart가 inventory를 메서드 파라미터로 받는다. addItem과 updateQuantity 호출 시마다 inventory를 전달한다. Cart와 Inventory는 고정된 협력 관계인데 굳이 왜 파라미터로 받아야 할까?

넷째, PromotionPolicy는 활성 프로모션을 찾는 역할만 한다. 프로모션 정책을 판단하지 않기도 하고, 이름과 실제 역할이 다르다.

## 오브젝트 책 관점에서의 문제

일단은 우테코 2주차 기간 중에 읽었던 오브젝트 책 내용을 기준으로 다시 생각해보자.

단일 책임 원칙: Inventory는 재고 관리 책임만 가져야 한다. 프로모션 정책 판단은 다른 클래스의 책임이다. 현재는 두 책임을 모두 가지고 있어서 응집도가 낮다.

명시적 의존성: 의존성은 생성자로 주입해야 한다. 메서드 파라미터로 전달되는 의존성은 숨겨진 의존성이다. Cart가 Inventory를 매번 파라미터로 받으면, 의존 관계가 호출 시점까지 드러나지 않는다. 생성자 주입이면 클래스 선언부만 봐도 의존 관계를 알 수 있다.

이름과 책임의 일치: PromotionPolicy는 프로모션 정책을 다룬다는 의미를 내포한다. 하지만 실제로는 활성 프로모션 찾기만 한다.

## 개선 방향 결정

두 가지 리팩토링이 필요했다.

첫째, PromotionPolicy를 강화한다. Inventory를 생성자로 주입받고, 프로모션 판단 로직을 여기로 이동한다. 그러면 PromotionPolicy가 이름에 맞게 프로모션 정책을 실제로 판단한다.

둘째, Cart에 Inventory를 주입한다. Cart 생성자에서 Inventory를 받아서 필드로 저장한다. 메서드에서 파라미터로 받을 필요가 없어진다.

이렇게 하면 책임이 명확해진다. Inventory는 재고 관리, PromotionPolicy는 프로모션 정책 판단, Cart는 장바구니 관리. 의존성도 모두 생성자로 명시적으로 주입된다.

## 단계별 리팩토링

한 번에 하나씩, 커밋하면서 진행했다.

1단계: Cart에 Inventory 주입

Cart 생성자에 inventory 파라미터를 추가하고 필드에 저장했다. cartStore에서 Cart 생성 시 inventory를 함께 전달하도록 수정했다.

```typescript
// Before
constructor(promotions: Promotion[])

// After
constructor(promotions: Promotion[], inventory: Inventory)
```

2단계: Cart 메서드에서 inventory 파라미터 제거

addItem과 updateQuantity에서 파라미터 대신 this.inventory를 사용했다. cartStore 호출부도 수정했다.

```typescript
// Before
addItem(product: Product, quantity: number, inventory: Inventory)

// After
addItem(product: Product, quantity: number)
```

3단계: PromotionPolicy 강화

생성자에 inventory를 추가했다. Inventory에 있던 canGetAdditionalFreeItem과 calculateFullPriceQuantity를 PromotionPolicy로 이동했다. 시그니처를 바꿔서 product만 받도록 했다. 내부에서 this.findApplicablePromotion으로 프로모션을 찾는다.

```typescript
// Before
class PromotionPolicy {
  constructor(promotions: Promotion[])
  findApplicablePromotion(product: Product)
}

// After
class PromotionPolicy {
  constructor(promotions: Promotion[], inventory: Inventory)
  findApplicablePromotion(product: Product)
  canGetAdditionalFreeItem(product: Product, quantity: number)
  calculateFullPriceQuantity(product: Product, quantity: number)
}
```

4단계: Inventory 정리

canGetAdditionalFreeItem과 calculateFullPriceQuantity를 삭제했다. Inventory는 이제 재고 관리만 담당한다.

## 리팩토링 후 구조

의존성 흐름:

- Cart → Inventory, PromotionPolicy
- PromotionPolicy → Inventory
- Inventory → 없음

책임 분리:

- Inventory: 재고 조회, 재고 검증
- PromotionPolicy: 활성 프로모션 검색, 추가 증정 판단, 정가 결제 수량 계산
- Cart: 상품 추가/제거/수정, 가격 계산

명시적 의존성:

모든 의존성이 생성자로 주입된다. Cart를 보면 Inventory와 PromotionPolicy가 필요하다는 걸 바로 알 수 있다. PromotionPolicy를 보면 Inventory가 필요하다는 걸 알 수 있다.

할 수 있다고 해서 해야 하는 건 아니다. Inventory가 재고 정보를 알고 있다고 해서 프로모션 판단까지 해야 하는 건 아니다. 재고 정보를 아는 것과 프로모션 정책을 판단하는 것은 다른 책임이다.

생성자 주입이 메서드 파라미터보다 명시적이다. 호출 시점이 아니라 생성 시점에 의존성이 드러난다. 협력 관계를 파악하기 쉽다.

이름은 책임을 반영해야 한다. PromotionPolicy라는 이름에 맞게 정책 판단 책임을 부여했다.

작은 단계로 나눠서 리팩토링하면 안전하다. 각 단계마다 커밋하고 동작을 확인했다.
